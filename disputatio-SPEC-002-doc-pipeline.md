# SPEC-002: Disputatio — пайплайн полировки пары «спека + план»

Статус: draft v0.1 · Дата: 2026-08-28
Область: автоматизация двух вложенных циклов полировки документов (spec-контур,
pair-контур) поверх протокола раундов SPEC-001. Ядро FSM сессии (SPEC-001 §2)
не меняется. Источник требования — правило флота
`spec-authoring.md` (prograph-vault#102), запрос — inbox-issue #44,
пункт плана — `todo://disputatio/spec-pair-polish-automation`.

---

## 1. Термины и роли

| Термин | Определение |
|---|---|
| **Pipeline** | Один запуск полировки пары от идеи до готового к публикации draft-PR-комплекта. |
| **Contour (контур)** | Вложенный цикл полировки: `spec` (спека до сходимости) или `pair` (совместная проверка спеки и плана). Каждый контур исполняется как **обычная сессия SPEC-001**. |
| **Revision (ревизия)** | Порядковый номер сессии контура: `spec-r1`, `pair-r1`, `spec-r2`, … Новая ревизия создаётся возвратом по архитектурному дефекту. |
| **Runner** | Оркестратор пайплайна. Управляет фазами, создаёт и интерпретирует сессии контуров. Не дублирует механизмы ядра: контур = «прогнать стандартную сессию до терминала». |
| **Checklist** | Закрытый набор условий сходимости контура. Два набора различны: spec converged и pair converged (§5). |
| **Defect class** | Класс blocker/major-находки pair-ревью: `architectural` (возврат к спеке) или `execution` (правка только плана). |
| **Pipeline manifest** | `pipeline.json` — текущее состояние пайплайна плюс append-only исторические коллекции (§4.2). |

Принципы SPEC-001 действуют — всё состояние на диске, всё общение через
артефакты фиксированной схемы, write-ahead, оркестратора можно убить в любой
точке и возобновить — с одним явно оформленным отклонением: семантика
`ESCALATED` следует runtime-контракту, а не нормативному тексту §2/§5.5
SPEC-001, до erratum (§7.2, §11).

Семантика домена жёсткая, обобщённого N-stage DSL нет: контуры `spec` и `pair`,
их чеклисты и правила возврата зашиты в код и схемы. Конфигурируются только
пути документов, агенты, лимиты, состав doc-гейтов и тексты чеклистов.

## 2. State machine пайплайна

```
IDLE ──► SPEC_LOOP ──► PAIR_LOOP ──► EXPORTING ──► DONE
             ▲              │
             └──────────────┘  architectural_defect
                               (новая spec-rN+1, затем всегда новая pair-rN+1)

SPEC_LOOP | PAIR_LOOP ──► ESCALATED ──► EXPORTING(partial) ──► DONE
любая нетерминальная фаза ──► FAILED
```

Таблица переходов закрытая и валидируется; переход вне таблицы — ошибка
реализации, немедленный `FAILED`.

| Из | В | Причина (`reason`, закрытый enum) |
|---|---|---|
| `IDLE` | `SPEC_LOOP` | `started` |
| `SPEC_LOOP` | `PAIR_LOOP` | `spec_converged` |
| `PAIR_LOOP` | `EXPORTING` | `pair_converged` |
| `PAIR_LOOP` | `SPEC_LOOP` | `architectural_defect` \| `external_spec_adopt` |
| `SPEC_LOOP` | `ESCALATED` | `session_deadlock` \| `session_budget_hit` \| `max_architectural_returns` \| `pipeline_budget_hit` |
| `PAIR_LOOP` | `ESCALATED` | те же |
| `ESCALATED` | `EXPORTING` | `export_partial` |
| `EXPORTING` | `DONE` | `exported` |
| любая **нетерминальная** | `FAILED` | `session_failed` \| `invariant_violation` |

`DONE` и `FAILED` терминальны: переходов из `DONE` нет вовсе (ретроактивно
признать завершённый результат failed нельзя — это была бы правка истории).

Инварианты пайплайна:

- **P1.** Каждый контур — полноценная сессия SPEC-001 со своим layout,
  артефактами и session-resume. Runner не заглядывает внутрь раундов, кроме
  чтения валидированных артефактов. Размещение нескольких сессий требует
  честного расширения сессионного контракта — разделения `workspace_root`
  и `artifact_root` (§4.1); FSM сессии при этом не меняется.
- **P2.** Write-ahead: намерение (`next_action`, §4.3) персистится в манифест
  **до** соответствующего действия; после завершения действия результат
  персистится до следующего намерения.
- **P3.** `outcome` завершённой сессии неизменяем. Перекрытие сходимости новой
  ревизией выражается отношением `superseded_by`, а не переписыванием
  исторического `outcome`.
- **P4.** Внутрисессионные события (continue-раунды, execution-правки плана)
  не являются pipeline-переходами. На уровень пайплайна сессия выходит
  собственным терминалом либо явным `park` от `RoundBoundaryPolicy` (§7.1);
  обычный continue pipeline-переходом не является.
- **P5.** После каждой новой сходимости спеки создаётся **новая** pair-сессия,
  даже если план не менялся: правило требует полную перепроверку пары.
- **P6.** Приоритет возврата: наличие хотя бы одной blocker/major-находки
  с `defect_class: architectural` в ревью раунда pair-сессии всегда
  ведёт в `SPEC_LOOP` — сколько бы execution-находок ни было рядом и
  какое бы стоп-условие §5 SPEC-001 ни сработало на этом раунде.
  Приоритет над `DEADLOCK`/`BUDGET_HIT` не декоративен: он обеспечен
  точкой опроса политики до `decide()` (§7.1), иначе исчерпанный бюджет
  на последнем раунде увёл бы дефектную спеку в эскалацию вместо
  переработки.
- **P7.** `ESCALATED` — честный частичный результат: экспорт выполняется,
  `converged: false`, причина эскалации в манифесте, CLI завершается ненулевым
  кодом. `FAILED` — невосстановимая ошибка: автоматический экспорт не
  выполняется; диагностический пакет собирает отдельная команда
  `disp pipeline export --partial`.
- **P8.** Повторный перевод уже `FAILED` пайплайна в `FAILED` идемпотентен и
  не добавляет дубликата transition в манифест. Гарантии двух файлов разные,
  потому что атомарно обновить оба одной операцией нельзя: **манифест —
  единственный source of truth** (строго без дубликатов), `events.jsonl` —
  производный **best-effort** диагностический поток (zero-or-more): событие
  может отсутствовать (падение между записью манифеста и события; resume
  пропущенные события не регенерирует) и может дублироваться — каждое несёт
  `operation_id`, которым **штатный читатель журнала** (пара к sink'у, §9)
  подавляет дубли — дедупликация не остаётся обязанностью гипотетического
  потребителя, а поставляется вместе с журналом; оборванная kill'ом
  последняя строка чинится при открытии (усечение частичного хвоста). Истина
  всегда восстановима из манифеста.
- **P9.** Целостность control plane: **перед каждым ходом автора** — где
  ход это один вызов адаптера, а не один раунд: внутри `drive()` их
  несколько по числу раундов, и ещё несколько внутри одного `PROPOSING`,
  если схема вывода невалидна и срабатывает `schema_retries` (§4.4
  SPEC-001). Обрамление шага целиком оставило бы подмену между
  retry-попытками невидимой. Runner write-ahead
  записывает pre-turn integrity snapshot (хеши неизменяемых управляющих
  файлов, длины+хеши append-only журналов) **одной записью — append'ом в
  `integrity_anchor`**, после хода сверяет: неизменяемые файлы —
  равенством хешей, append-only журналы — prefix-property (старое
  содержимое — неизменённый префикс нового). Расхождение → `FAILED`
  (`invariant_violation`). Исполнительный seam — порт
  `SessionLifecyclePolicy` (§7.1): `before_author_turn` пишет snapshot,
  `after_author_turn` сверяет до чтения артефактов хода. Snapshot durable,
  поэтому kill во время хода автора не открывает окно: resume проводит ту
  же сверку по последней записи анкера **до** чтения потенциально
  подменённых артефактов (§8.1 шаг 0).

  **Снапшот пишется ровно в один файл — в анкер, и больше никуда.**
  Дублирование его в манифест потребовало бы согласовать две независимые
  файловые границы, чего одной атомарной операцией не сделать: падение
  между записями оставило бы расхождение, неотличимое от подмены, и
  штатный крах читался бы как tampering. Поэтому манифест снапшота не
  хранит; истина целостности — анкер, истина состояния пайплайна —
  манифест, и пересечения у них нет. Запись анкера идемпотентна по ключу
  `{session_id, round, operation_id}`: повтор после краха даёт ту же
  строку, а запись о ходе, который не начался, сверку не ломает — она
  описывает состояние, которое никто не менял.

  **Анкер самодостаточен для bootstrap'а сверки.** Identity незавершённого
  хода берётся ИЗ последней записи анкера, а не подаётся в него: иначе
  порядок §8.1 замкнулся бы в круг — сверка обязана предшествовать чтению
  манифеста, а `session_id`/`round` пришлось бы взять из того самого
  манифеста, который и мог быть подменён. Поэтому запись несёт полную
  identity, а читатель умеет «последняя запись журнала» без аргументов.
  Оба входа, нужных, чтобы найти файл, лежат вне рабочего дерева:
  `<anchor_root>` — из живой конфигурации (не из снапшота в каталоге
  пайплайна: он автору достижим), `<anchor_id>` — из `--slug` оператора.

  **Записи двух видов, и это обязательно.** `pre_turn` — снапшот перед
  ходом; `turn_completed` — отметка после успешной сверки, с той же
  identity. Без второй вида ход, завершённый штатно, оставлял бы
  последней запись `pre_turn`, а runtime сразу после сверки законно пишет
  артефакты раунда и двигает `session.json` — и следующий `resume`
  прочитал бы эти штатные изменения как подмену, уронив пайплайн в
  `FAILED` на ровном месте. Поэтому `after_author_turn` при успехе
  дописывает `turn_completed` (журнал остаётся append-only, ничего не
  переписывается), а сверка на resume применяется, только если последняя
  запись — `pre_turn`: именно она означает ход, прерванный на середине.

  Причина, по которой граница вообще нужна: право записи автора
  распространяется на рабочую директорию, а `.disputatio` намеренно
  исключён из диффа раунда — запись автора туда невидима и для
  `changes.patch`, и для `doc-scope`.

  **Гарантия — обнаружение, а не предотвращение**, и якорь доверия —
  файловая граница, а не обещание адаптера. Adapter-level запрет записи по
  путям якорем быть не может: автору нужен Bash для работы над
  репозиторием, а deny на инструменты правки файлов не покрывает запись
  через shell — то есть автор, перезаписавший разом и манифест, и снапшот
  внутри него, лишил бы сверку опоры. Поэтому **`integrity_anchor` —
  append-only журнал pre-turn снапшотов — хранится вне рабочего дерева
  автора**. Манифест хранит только логический `anchor_id`
  (машинно-независимый, равен `pipeline_id`); физическое расположение
  резолвится при запуске из конфигурации: `<anchor_root>/<anchor_id>.jsonl`,
  где `anchor_root` — `anchor_path` §3.2 (дефолт — пользовательский
  state-каталог). Разделение не косметическое: канонические поля манифеста
  не несут абсолютных и машинно-зависимых путей (§4.2), а расположение
  анкера машинно-зависимо по природе — его место в конфиге, не в манифесте.
  Резолв внутрь `workspace_root` — отказ старта (fail-closed): анкер,
  лежащий в дереве автора, анкером не является. Проверяется канонизованный
  путь — после `expanduser`, раскрытия `..` и symlink'ов (`resolve`), —
  и проверяется заново при каждом `resume`, а не только при `run`.

  **Модель угроз честная.** P9 ловит непреднамеренную запись, дрейф модели
  и осечку инструмента в пределах рабочего дерева — то, что реально
  случается. Агент, целенаправленно ищущий control plane за пределами
  своего workspace, произвольным shell'ом не сдерживается ничем, кроме
  изоляции уровня ОС; она — вне v1 (§11). Adapter-level path-deny остаётся
  **необязательным** слоем глубины: адаптер, умеющий его, объявляет
  capability и получает deny на `.disputatio/**`; адаптер без неё
  допускается (отказ по этому признаку был бы платой без гарантии).

## 3. CLI и конфигурация

### 3.1 Команды

```
disp pipeline run     --slug <slug> [--task <файл|строка>] [--config <toml>]
disp pipeline resume  --slug <slug> [--config <toml>]
                      [--discard-round | --adopt-external]
disp pipeline status  --slug <slug> [--config <toml>]   # строго read-only
disp pipeline export  --slug <slug> [--config <toml>] [--partial]
```

Флаги `resume` — два исхода остановки на неатрибутируемом dirty state
(§8.1), применимы к активной сессии любого контура, взаимоисключающи,
без остановки — ошибка «нечего решать»:

- `--discard-round` — санкционировать reset и переиграть раунд; ручные
  правки сознательно теряются;
- `--adopt-external` — принять правку как внешнюю. Принятие durable в git:
  диф коммитится **операторским чекпоинтом** (`disputatio: operator adopt
  <slug>`, в теле коммита — trailer `Disputatio-Operation: <operation_id>`),
  патч дополнительно сохраняется артефактом
  `adoptions/<operation_id>.patch` в каталоге пайплайна (sha256 — в
  operator decision). Активная сессия паркуется (`outcome: abandoned`,
  `superseded_by` — новая ревизия); новая ревизия создаётся с `base_commit`
  = операторский чекпоинт — reset её первого `PROPOSING` идёт к нему, и
  принятая правка не стирается.

**Scope принимаемого дифа — fail-closed.** Adoption не обходит документную
дисциплину. Scope вычисляется по полному `git status` (tracked и untracked
вместе) **за вычетом каталога оркестратора `.disputatio/`** — тем же
исключением, каким SPEC-001 убирает его из диффа раунда: пайплайн сам
непрерывно порождает там untracked-файлы (§4.1), и буквальный полный
status отвергал бы каждый adoption по собственному журналу. Исключение
именно узкое: путь под `.disputatio/`, оказавшийся **tracked-изменённым**,
adoption отклоняет — это как раз внешняя правка control plane, которую
fail-closed норма обязана поймать, а не спрятать. В оставшемся наборе
правка или новый файл допустимы только по путям `spec_path`/`plan_path`
(новый untracked документ — легальный случай, например план, которого ещё
нет; его содержимое входит в канонический adoption patch и чекпоинт);
любой иной путь — tracked или untracked — отклоняет adoption целиком
(такую правку пайплайн не принимает — она
разбирается вне его, посторонний untracked не переживает adoption молча).
Маршрут новой ревизии определяется путями дифа, а не только классификацией
ревьюера:

- spec-контур: допустим только `spec_path` → новая spec-ревизия;
- pair-контур, затронут только `plan_path` → новая pair-ревизия;
- pair-контур, затронут `spec_path` → **обязательный возврат в
  spec-ревизию**, независимо от того, выдал ли ревьюер architectural
  finding: спека, изменившаяся после своей сходимости, обязана пройти
  spec-контур заново. Приоритет P6 действует поверх: обнаруженный
  архитектурный дефект ведёт в spec-ревизию и при чистом `plan_path`-дифе.

**Write-ahead протокол обоих решений** — те же интенты §4.3 (без них
падение посреди многошаговой мутации было бы неразрешимо):

- `adopt_external`: intent записывается **до** первой мутации
  (`operation_id` детерминирован из sha256 дифа + identity активного
  session/round-чекпоинта — adopt применим и к in-flight сессии, не только
  к припаркованной); исполнение идемпотентно — patch-файл пишется по имени
  `operation_id`, git-чекпоинт распознаётся по trailer'у (падение после
  commit, до записи решения: resume видит intent, находит чекпоинт по
  trailer'у и продолжает без второго коммита); commit point — одна
  атомарная запись манифеста, и она **единственная** пишет outcome (P3):
  operator decision + `outcome: abandoned` + `superseded_by` + при маршруте
  в spec-ревизию — pipeline-переход `PAIR_LOOP → SPEC_LOOP` с reason
  `external_spec_adopt` в той же записи + chained `next_action =
  create_session` новой ревизии напрямую. `record_return` в adoption-пути
  **не участвует**: он определён исключительно для настоящего architectural
  finding и никогда не перезаписывает уже записанный `abandoned`. Если
  маршрут в spec вызван обеими причинами сразу или только дефектом —
  commit point всё равно один, outcome один (`abandoned`), а `reason`
  перехода выбирается по причине маршрута: изменение `spec_path` →
  `external_spec_adopt`; только архитектурный дефект при plan-only дифе →
  `architectural_defect`; обе причины → `external_spec_adopt` как основной,
  архитектурные находки — в evidence того же transition/operator decision,
  без второй записи outcome;
- `discard_round`: intent до reset; reset идемпотентен; commit point —
  запись operator decision. Падение между reset'ом и записью не теряет
  факт санкции: intent с `operation_id` уже durable, replay дописывает
  решение.

`run` исполняется в целевом git-репозитории (рабочая директория — предмет
работы, как у обычной сессии). Предусловия `run`, проверяемые fail-closed:

- рабочее дерево чистое: **нет изменений tracked-файлов и нет untracked-путей
  вне `.disputatio/`**. Исключение ровно одно и узкое — собственный control
  plane оркестратора: несколько пайплайнов сосуществуют под разными
  `<slug>` (§4.1), и чужой каталог пайплайна — штатное состояние, а не
  грязь. Любой другой untracked-файл старт **блокирует**, и это не
  придирка к чистоте: первый же `PROPOSING` делает `git reset --hard` и
  `clean` по всему дереву (минус каталог сессии), то есть посторонний
  untracked-файл был бы молча уничтожен без санкции оператора. Пропустить
  его — значит нарушить ту же норму, по которой resume запрещает
  destructive reset поверх неатрибутируемого состояния (§8.1), а adoption
  отклоняет посторонний untracked целиком (выше). Прецедент `preflight`
  SPEC-001 здесь не наследуется: его терпимость к untracked рассчитана на
  единственный ожидаемый untracked — `.disputatio/`;
- текущая ветка — не base/protected ветка репозитория (проверяется
  конфигурируемый список `protected_branches`, по умолчанию `master`, `main`,
  а не только имя `master`). **Runner ветку не создаёт** — это внешний эффект;
  при неподходящей ветке `run` отказывает и печатает подготовительную команду
  (`git switch -c docs/<slug>`);
- каталог `.disputatio/pipelines/<slug>/` не существует (существует —
  использовать `resume`);
- канонизованный `anchor_path` (после `expanduser`, `..` и symlink'ов)
  резолвится **вне** `workspace_root` (P9) — иначе отказ; та же проверка
  повторяется при каждом `resume`.

После успешных предусловий `run` **первым делом создаёт пустой анкер**
`<anchor_root>/<anchor_id>.jsonl` — до любой сохраняемой мутации
пайплайна. Тогда крах на ранних intent'ах (`create_session` и раньше) не
делает пайплайн невозобновимым, а «файла анкера нет» на `resume`
однозначно означает неверное расположение, а не раннюю стадию запуска.

`pipeline_id = slug` (грамматика `[a-z0-9][a-z0-9._-]{0,63}`); коллизия — отказ.

### 3.2 Конфиг: секция `[pipeline]`

```toml
[pipeline]
spec_path = "docs/specs/2026-08-28-foo-design.md"
plan_path = "docs/plans/2026-08-28-foo-plan.md"
max_architectural_returns = 2      # возвраты PAIR→SPEC; spec-r1 не считается
soft_max_pipeline_tokens = 0       # 0 = выключено; см. §7.2
soft_max_pipeline_wall_seconds = 0
protected_branches = ["master", "main"]
# anchor_path — КАТАЛОГ журналов целостности P9 (`anchor_root`); внутри
# него анкер зовётся <anchor_id>.jsonl. ОБЯЗАН резолвиться вне
# workspace_root; дефолт — пользовательский state-каталог. Значение
# машинно-зависимо и потому живёт здесь, а не в манифесте (§4.2)
# anchor_path = "~/.local/state/disputatio/anchors"
# checklists.spec / checklists.pair — переопределение дефолтов (§5.3)
# gates — дополнительные doc-гейты сверх обязательного baseline (§6)

[agents.author]    # как в сессии SPEC-001
[agents.reviewer]
[limits]           # пер-сессионные лимиты SPEC-001, общие для обоих контуров
```

При `run` снапшотятся **и конфиг, и исходный task/prompt**: копии кладутся в
каталог пайплайна, манифест хранит их относительные пути и sha256. Действующие
чеклисты (дефолт или override) снапшотятся туда же с хешем — сходимость
доказуемо объявлена по конкретным условиям.

## 4. Раскладка на диске и манифест

### 4.1 Layout

```
.disputatio/
  pipelines/
    <slug>/
      pipeline.json        # PipelineState (§4.2), атомарная перезапись
      config.toml          # снапшот конфига
      task.md              # снапшот исходного prompt
      checklists.toml      # снапшот действующих чеклистов
      events.jsonl         # append-only события уровня пайплайна
      adoptions/           # патчи принятых внешних правок (§3.1)
      sessions/
        spec-r1/           # artifact_root сессии: внутри — её .disputatio/
        pair-r1/
        spec-r2/
        pair-r2/
      result/              # экспорт (§8)
```

Несколько запусков сосуществуют под разными `<slug>`; история не теряется,
resume однозначен. События сессий остаются в их собственных `events.jsonl`;
пайплайновый лог не дублирует их и несёт только своё: `phase_change`,
`session_started`, `session_finished`, `return_recorded`, `exported`, `error`.

**Разделение `workspace_root` / `artifact_root`.** Действующий контракт
хранения — «одна рабочая директория — одна сессия»: `FileStateStore` и
построитель путей жёстко связывают состояние с `root/.disputatio`, а `root`
одновременно считается git-репозиторием. Разместить `sessions/spec-r1/`
внутри него описанным образом нельзя — все ревизии конфликтовали бы за один
`session.json`. Поэтому SPEC-002 **явно расширяет сессионный контракт**:
composition root и построитель путей принимают отдельный `artifact_root`
(хранилище `.disputatio`-состояния сессии) при прежнем `workspace_root`
(git-операции). По умолчанию `artifact_root = workspace_root` — существующее
поведение сохраняется байт-в-байт; ADR-006 переформулируется в «один
artifact_root — одна сессия». Pipeline передаёт
`artifact_root = pipelines/<slug>/sessions/<revision>/`,
`workspace_root =` корень репозитория.

### 4.2 Схема манифеста — `disputatio/pipeline/v1`

`pipeline.json` — **текущее состояние**, перезаписываемое атомарно
(temp-file + rename). Append-only в нём — исторические коллекции
(`transitions`, `operator_decisions`, списки сессий); плюс отдельный event
log. **Append-only означает prefix-equality, а не «длина не уменьшается»:**
уже записанные элементы обязаны совпадать поэлементно, новые допускаются
только в хвост. Хранилище проверяет это при каждой записи (§9, `events`);
переписывание элемента на месте — та же порча истории, что и усечение, и
отвергается так же. Единственное разрешённое изменение прежнего элемента —
поля, объявленные заполняемыми позже: `outcome` (с `null` на значение,
однократно, P3) и `superseded_by`. Все пути — относительные (к корню
репозитория или каталогу пайплайна); абсолютных путей и машинно-зависимых
значений в манифесте нет — расположение анкера поэтому и живёт в конфиге,
а манифест несёт только логический `anchor_id` (P9).

Временные метки различаются по природе:
operational-манифест несёт метки **фактов** (`created_at` пайплайна,
`at` переходов) — они записываются один раз и стабильны; канонический экспорт
(§8.2) эти фиксированные метки сохраняет, а запрещено в нём только время,
порождаемое самим актом экспорта.

Поля (pydantic, `"schema": "disputatio/pipeline/v1"`):

- `pipeline_id`, `created_at`;
- `phase`: `IDLE | SPEC_LOOP | PAIR_LOOP | EXPORTING | ESCALATED | DONE | FAILED`;
- `task`: `{path, sha256}`; `config`: `{path, sha256}`;
  `checklists`: `{path, sha256}`;
- `documents`: `{spec_path, plan_path}`;
- `spec_sessions`, `pair_sessions` — append-only списки записей:
  `{revision, session_id, path, entry_hashes, outcome, superseded_by}`, где
  `entry_hashes` — состояние обоих документов на входе сессии (аудит и
  доказательство, относительно какой пары шло ревью): по каждому из
  `spec_path`/`plan_path` — sha256 либо явный маркер `absent` (план в
  spec-r1 законно отсутствует); хеши task/config/checklists сюда не входят —
  они верхнеуровневые и неизменны на весь пайплайн,
  `outcome` — **pipeline-интерпретация исхода**, неизменяемая после записи:
  `null | converged | escalated | failed | architectural_defect | abandoned`
  (`abandoned` — сессия оставлена решением оператора `--adopt-external`).
  `architectural_defect` — исход **припаркованной** pair-сессии (§7.1): её
  собственный FSM-терминал не достигнут и не подделывается, сессия просто
  больше никогда не продвигается. `superseded_by` — ссылка на ревизию,
  перекрывшую эту (`null`, пока не перекрыта);
- `transitions` — append-only: `{from, to, reason, evidence, at}`; `evidence` —
  список структурированных ссылок `{session_id, round, finding_id}`;
- `budget_used` — агрегат (`tokens`, `wall_seconds`, `cost_usd_est`),
  **детерминированно пересчитываемый** из `session.json` всех сессий —
  включая припаркованные, их расход тоже потрачен — при каждой записи
  манифеста, а не инкрементируемый независимо: повторный `run_session` не
  даёт двойного начисления по построению;
- `operator_decisions` — append-only: `{operation_id, kind: discard_round |
  adopt_external, at, worktree_diff_sha256}` — provenance вмешательств
  оператора (§3.1);
- `anchor_id` — логическое имя `integrity_anchor` (P9), равно
  `pipeline_id`; физический путь в манифест не пишется (он машинно-зависим
  и резолвится из конфига). Снапшотов манифест не хранит вовсе — они живут
  только в анкере, форма записи там:
  `{session_id, round, operation_id, immutable: {path: sha256},
  append_only: {path: {prefix_bytes, prefix_sha256}}}` — по
  `prefix_bytes`/`prefix_sha256` проверяется prefix-property журнала,
  по `sha256` — равенство неизменяемого файла;
- `next_action` — write-ahead intent (§4.3) или `null`.

### 4.3 Write-ahead intent (`next_action`)

Смены фазы недостаточно для crash recovery: падение между созданием каталога
сессии и записью `session_started` породило бы при resume дубликат. Поэтому
каждое действие runner'а проходит цикл:

1. записать `next_action` = `{operation_id, kind, args}` в манифест;
2. выполнить действие (идемпотентно относительно `operation_id`);
3. записать результат и `next_action = null` **либо intent-преемник**
   (atomic chaining): та же атомарная запись вправе заменить выполненный
   intent следующим — с `predecessor_operation_id` для provenance; ровно так
   commit возврата §7.3 завершается `next_action = create_session`, минуя
   промежуточный `null`.

`kind` — закрытый enum: `create_session | run_session | finish_session |
record_return | adopt_external | discard_round | export`. Resume читает
`next_action` и допроигрывает незавершённое действие; идемпотентность
каждого `kind` — обязательное
требование к реализации и предмет тестов (§10).

## 5. Doc-сессии: режим, схема ревью, сходимость

### 5.1 Режим `document`

В contracts добавляется `Mode.DOCUMENT` (аддитивно к `develop | analyze`).
Обе сессии контуров идут в этом режиме. Задача автора:

- spec-контур: довести документ `spec_path` до сходимости (spec-r1 — написать
  по task; spec-rN — переработать по архитектурным находкам);
- pair-контур: написать/переработать `plan_path` по сошедшейся спеке.
  **Автор pair-контура не имеет права менять спеку** — архитектурный дефект
  паркует pair-сессию и возвращает пайплайн к спеке (§7.1, §7.3), а не даёт
  право правки.

Анти-сикофантия SPEC-001 §5 действует без изменений: исключение раунда 1
касается только `analyze` без правок, значит doc-сессия с написанным
документом получает минимум один содержательный цикл ревью. Это свойство
закрепляется тестом первого раунда (§10).

**Версионирование (по правилу SPEC-001 §4 «несовместимые изменения → v2»):**
расширение закрытого enum несовместимо для строгого v1-reader, поэтому v1 не
переопределяется ретроактивно. Артефакты doc-сессий пишутся со схемой
**`disputatio/v2`** — строгим надмножеством v1: `Mode.DOCUMENT`,
`Review.checklist`, `Issue.defect_class`. v2-reader принимает v1; сессии
`develop`/`analyze` продолжают писать v1 без изменений. Пайплайновые
артефакты — отдельное семейство `disputatio/pipeline/v1` (§4.2).

### 5.2 Расширение схемы ревью

Аддитивно к `Review` (в составе `disputatio/v2`, §5.1):

```jsonc
"checklist": [                    // обязателен в Mode.DOCUMENT
  {
    "id": "S1",                   // id из чеклиста своего контура, §5.3
    "status": "pass | fail | not_applicable",
    "evidence": [                 // непустой при ЛЮБОМ статусе
      {"kind": "artifact", "ref": "docs/specs/...md", "lines": "34-41"},
      {"kind": "gate", "ref": "doc-links"}
    ],
    "issue_ids": ["R2-1"]         // обязателен и непуст при status=fail
  }
]
```

У `Issue` — новое опциональное поле `defect_class: architectural | execution`.

Валидационные правила проверяются **до деградации безевиденсных
blocker/major до `minor`** (§4.4 SPEC-001): деградация — милосердие к
голословному замечанию, а не разрешение противоречивому ревью пройти.
Иначе `approve` с безевиденсным blocker'ом, `S1: pass` и без
`defect_class` прошёл бы V5/V7/V8, потому что к моменту их проверки
blocker'а в артефакте уже нет.

Сами правила (слой §4.4 SPEC-001, анти-галлюцинационное ядро;
нарушение → schema-invalid → retry с текстом ошибки, до `schema_retries`,
затем `FAILED` — существующий малый лимит, бесконечного расхода бюджета нет):

- **V1.** `checklist` обязан покрыть ровно набор id чеклиста своего контура —
  без пропусков и чужих id.
- **V2.** `evidence` непуст у каждого пункта независимо от статуса: pass и
  not_applicable без указания, что именно проверено/почему неприменимо, —
  голословны. Формы evidence закрыты: ссылка на артефакт с диапазоном строк
  или ссылка на результат гейта.
- **V3.** `approve` несовместим с `status: fail` у любого пункта (симметрия
  правилу «approve при `verification.overall == fail` отвергается»).
- **V4.** Каждый `fail` обязан ссылаться через `issue_ids` на существующие
  issues этого же ревью с severity ≥ major; валидатор проверяет существование
  ссылок и severity. Иначе цикл нечем двигать.
- **V5.** Pair-контур: `defect_class` обязателен у **каждой** blocker/major
  находки. Отсутствие — schema-invalid → retry (не downgrade: класс дефекта
  определяет маршрут возврата, угадывать его молча нельзя).
- **V6.** Следствие V1–V4, V7: до `decide()` не доживает `approve`, нарушающий
  чеклист. `core/deciding.py` не меняется; converged doc-сессии = критерий
  §5.1 SPEC-001. Гарантия закрепляется интеграционным тестом (§10), а не
  промптом.
- **V7.** В `Mode.DOCUMENT` `approve` несовместим с наличием blocker/major
  issues в этом же ревью — не только с checklist-fail. Ревью «одобряю, но вот
  блокер» внутренне противоречиво и отвергается на валидации.
- **V8.** Согласованность чеклиста с находками: `S1: pass` несовместим с
  blocker/major issues того же ревью (машинная проверка); в общем виде пункт,
  условие которого опровергается issue этого ревью, обязан иметь `status:
  fail` и ссылаться на неё через `issue_ids` — для прочих пунктов это
  требование промпта ревьюера, детерминированно enforced ровно там, где связь
  машинно-выводима (S1).

### 5.3 Чеклисты сходимости

Дефолтные тексты — вендоренная пинованная копия условий правила
`spec-authoring.md` (редакция 2026-08-26, prograph-vault#102), лежит в пакете
с provenance-заголовком (источник, дата, редакция). Override через конфиг
снапшотится и хешируется (§3.2). Пункты формулируются так, чтобы всегда иметь
осмысленный вердикт; `not_applicable` допустим только с обоснованием в
evidence.

**spec converged** (`S1`–`S5`): S1 нет blocker/major-находок; S2 нет
нерешённых архитектурных вопросов и TBD; S3 состояния ошибок и authority
определены; S4 интерфейсы и не-цели согласованы; S5 ссылки и факты проверены
по коду (механическую часть S5 закрывают doc-гейты §6, ревьюер ссылается на
их результаты).

**pair converged** (`P1`–`P5`): P1 каждая нормативная часть спеки покрыта
задачей плана; P2 план не вводит решений, которых нет в спеке; P3 порядок
реализации сохраняет рабочее или явно описанное промежуточное состояние;
P4 тесты доказывают требования, включая fail-closed пути; P5 команды проверки
и границы репозиториев выполнимы.

Детерминированная проверка трассируемости P1 (по REQ-id-конвенции) — вне v1:
осознанно оставлена LLM-ревью до проектирования формата идентификаторов;
архитектура гейтов (§6) обязана позволить добавить такой гейт без изменения
runner и FSM.

## 6. Doc-гейты (verifier)

Новые гейты в пакете `verifier`, те же контракты `GateResult`: стабильный
машинно-читаемый результат с кодом ошибки и evidence. Инвариант SPEC-001
сохраняется: `fail` гейтов не блокирует переход к ревью (ревьюер взвешивает
провал сам, результаты гейтов идут ему как диагностика), но блокирует
`CONVERGED`.

Все пять гейтов v1 — **обязательный baseline режима `document`**: конфиг
может только добавлять гейты, но не отключать baseline. Иначе отключённый
`doc-line-refs` позволил бы объявить сходимость без скриптовой проверки
якорей — ровно того требования правила, ради которого verifier-стадия
существует. Флага unsafe-отключения в v1 нет.

| Гейт | Проверяет |
|---|---|
| `doc-paths` | существование путей, **заявленных как существующие** (см. ниже) |
| `doc-links` | разрешимость относительных Markdown-ссылок |
| `doc-anchors` | существование локальных section anchors |
| `doc-line-refs` | корректность ссылок `file:line`; при наличии якорного текста в форме ссылки — совпадение строки с ним |
| `doc-scope` | диф раунда трогает только разрешённые пути: `spec_path` в spec-контуре, `plan_path` в pair-контуре |

Правила распознавания и нормализации (фиксируются реализацией и тестами):

- **Утверждение о существовании отличается от объявления намерения.**
  Документы этого пайплайна проектируют ещё не написанный код: спека и
  план законно называют `runtime/pipeline_runner.py`, которого нет. Гейт,
  требующий существования от каждого упомянутого пути, не дал бы сойтись
  ни одной спеке до реализации — то есть запретил бы ровно то, ради чего
  пайплайн существует. Поэтому `doc-paths` роняет раунд только на формах,
  которые **утверждают** существование: цель Markdown-ссылки, ссылка
  `file:line` и путь в декларации «правим существующее» (`Modify:`,
  `Test:` в блоке файлов задачи). Путь под `Create:` — объявление
  намерения: гейт его не требует и, наоборот, отмечает `warning`, если
  файл уже есть. Прочий путь в inline-code — `warning` при отсутствии, не
  `fail`.
- **Явный поддерживаемый синтаксис.** Проверяются только формы, которые
  парсер распознаёт однозначно: Markdown inline/reference-ссылки, автоссылки,
  пути и `file:line` в inline-code (`` `path/to/file.py:42` ``). Неизвестные
  или неоднозначные формы — пропуск либо отдельный `warning`, **не fail**:
  эвристика по «похожему на путь» тексту запрещена.
- **Нормализация якорей** — по правилам GitHub-flavored slugger: приведение
  регистра, пробелы → дефисы, обращение с Unicode и percent-encoding,
  суффиксы `-1`, `-2` для повторяющихся заголовков. Правила фиксируются
  тестами, чтобы результат не зависел от renderer.
- **Containment.** Целевой путь после нормализации (`..`, symlink resolution)
  обязан остаться внутри корня репозитория; symlink-переход наружу —
  нарушение с собственным кодом ошибки.

bench-verify (research-bench) — референс поведения и тест-кейсов; код не
вендорится.

## 7. Runner: контуры, возврат, лимиты

### 7.1 Перехват на границе раунда (FSM сессии не меняется)

FSM сессии SPEC-001 не расширяется: ни нового `Outcome`, ни новых переходов,
ни правок `core/machine.py`. Но существующий `drive()` крутит сессию до
терминала без точки возврата управления, поэтому граница раунда — **честное
расширение runtime-протокола** (не «существующий session-resume»): новый
порт `RoundBoundaryPolicy` — чистая функция над валидированным
`review.json`, которую `drive()` опрашивает **после записи `review.json` и
ДО вызова `decide()`**. Точка выбрана именно так, а не после `CONTINUE`:
`decide()` идёт строго top-down (converged → budget_hit → осцилляция →
max_rounds → continue, `core/deciding.py`), и на последнем разрешённом
раунде или при исчерпанном бюджете он вернул бы `DEADLOCK`/`BUDGET_HIT`
раньше ветки `CONTINUE` — политика не была бы опрошена вовсе, а
архитектурная находка ушла бы в эскалацию вместо обязательного возврата к
спеке. P6 требует обратного: возврат приоритетнее сессионных
стоп-условий, потому что спека, признанная дефектной, обесценивает и
исчерпанный бюджет, и достигнутый потолок раундов — продолжать
дебатировать план по неверной спеке незачем.

Вердикты: `proceed` — `decide()` вызывается штатно, дальше всё как
сегодня; `park` — `decide()` **не вызывается**, `decision.json` раунда не
пишется, `drive()` возвращает управление с текущим нетерминальным
состоянием. Без политики (default) поведение `drive()` байт-в-байт
сегодняшнее. Для pair-контура runner передаёт политику:

- нет blocker/major с `defect_class: architectural` → `proceed`;
- есть → `park`. Сессия остаётся припаркованной в записанном write-ahead
  состоянии (`DECIDING`, решение не принято); её FSM-терминал не
  достигнут и существующим именем (`ESCALATED` и т.п.) не называется —
  pipeline-интерпретация `architectural_defect` живёт только в манифесте
  (§4.2), сессия помечается `superseded_by` и больше никогда не продвигается
  (припаркованность runner распознаёт по манифесту, а не по состоянию
  сессии — §8.1 шаг 2).

Для spec-контура политика не передаётся (сессия гонится до собственного
терминала).

Второе расширение того же класса — порт **`SessionLifecyclePolicy`** с двумя
точками: `before_author_turn` (вызывается `drive()` перед запуском адаптера
автора на каждом `PROPOSING`) и `after_author_turn` (после возврата автора,
до чтения артефактов хода). Обе — чистые относительно сессии: состояние FSM
не меняют, ошибка политики → `FAILED`. Default — no-op (текущее поведение
байт-в-байт). Pipeline реализует ими P9: запись и сверку integrity
snapshot'а.

### 7.2 Интерпретация терминалов и лимиты

Runtime возвращает только `DONE`/`FAILED`; состояния `DEADLOCK`/`BUDGET_HIT`
проходят **внутрисессионную** цепочку `→ ESCALATED → EXPORTING(partial) →
DONE` целиком и автоматически — так устроена реализация v1: терминальные
цепочки (`_TERMINAL_CHAINS` в `core/machine.py`) не содержат интерактивного
шага, резолюция происходит **после** DONE, вне сессии, чтением частичного
экспорта. **Оформленное отклонение от нормативного текста SPEC-001**: §2 и
§5.5 SPEC-001 назначают в `ESCALATED` активного пользователя *до* экспорта —
реализация, принятая suite, этого шага не имеет, и расхождение существует
независимо от SPEC-002. SPEC-002 явно следует **runtime-контракту**, а
выравнивание текста SPEC-001 (erratum §2/§5.5 под фактическую семантику
«резолюция после DONE») вынесено отдельным изменением (§11). Нового порта не
требуется: в составе пайплайна читателем частичного экспорта выступает
runner — экспорт сессии остаётся в её layout и pipeline-экспортом не
дублируется, эскалация поднимается на уровень пайплайна. Runner
интерпретирует итог по **durable-состоянию** (история `session.json`,
`decision.json` последнего раунда), не по новым возвратам runtime — исходная
причина остановки не теряется:

| Сессия | Итог по durable-состоянию | Действие runner |
|---|---|---|
| spec | `DONE` через `CONVERGED` | → `PAIR_LOOP`, новая pair-rN |
| spec | `DONE` через `DEADLOCK`/`BUDGET_HIT` | → `ESCALATED` (причина из decision) |
| spec | `FAILED` | → `FAILED` пайплайна |
| pair | `DONE` через `CONVERGED` | → `EXPORTING` |
| pair | `park` от политики §7.1 (нетерминальная) | возврат §7.3 |
| pair | `DONE` через `DEADLOCK`/`BUDGET_HIT` | → `ESCALATED` (причина из decision) |
| pair | `FAILED` | → `FAILED` пайплайна |

Лимиты:

- `max_architectural_returns` — число возвратов `PAIR_LOOP → SPEC_LOOP`;
  spec-r1 не считается. Превышение → `ESCALATED`.
- `soft_max_pipeline_tokens` / `soft_max_pipeline_wall_seconds` — **soft**
  лимиты: проверяются между сессиями (сессия атомарна для бюджета пайплайна)
  и потому могут быть превышены последней сессией — имя и семантика честно
  это фиксируют. Жёсткие пайплайн-лимиты потребовали бы проверки между
  раундами — вне v1. Пер-сессионные лимиты SPEC-001 действуют как раньше.

### 7.3 Возврат по архитектурному дефекту: reconciliation

Runner узнаёт о дефекте **после** того, как runtime сессии уже durable-но
записал ревью и решение раунда — порядок возврата строится от этого факта
(reconciliation), а не от воображаемого владения результатом заранее:

1. **обнаружение**: durable-артефакт раунда `review.json` существует
   (`decision.json` у припаркованного раунда нет);
   runner читает их и вычисляет identity checkpoint'а —
   `{session_id, round, sha256(review.json)}`. Достаточно именно
   `review.json`: у припаркованного раунда `decision.json` не существует
   (§7.1 — `decide()` не вызывался), и identity обязана опираться на то,
   что записано;
2. **intent**: записать `next_action = record_return` с `operation_id`,
   детерминированно выведенным из identity checkpoint'а, и evidence
   (ссылки `{session_id, round, finding_id}`). Повторное обнаружение того же
   checkpoint'а при resume даёт тот же `operation_id` — шаг идемпотентен;
3. **cleanup worktree**: незакоммиченный pair-раунд уже изменил план, и его
   судьба определяется явно: диагностические артефакты раунда сохранены
   (они уже durable в layout сессии — `changes.patch`, `review.json`,
   `decision.json`), после чего worktree восстанавливается к последнему
   принятому commit/checkpoint (`git reset --hard`, тот же механизм, каким
   SPEC-001 делает `PROPOSING` re-runnable). В живом прогоне дерево
   принадлежит оркестратору и происхождение его состояния известно
   в процессе; на resume этот шаг исполняется **только после** сверки
   worktree §8.1 (шаг 3) — destructive reset поверх непроверенного дерева
   запрещён той же нормой, что и в модели внешней правки. Шаг идемпотентен:
   повтор reset к тому же коммиту — no-op;
4. **commit возврата** — ровно **одна атомарная запись** `pipeline.json`,
   несущая всё сразу: transition `PAIR_LOOP → SPEC_LOOP`, `outcome:
   architectural_defect` припаркованной pair-rN, `superseded_by` перекрытых
   ревизий и `next_action = create_session` для spec-rN+1. Это и есть commit
   point возврата: до этой записи возврат не случился (повтор идёт с шага 2
   по тому же `operation_id`; уже выполненный reset шага 3 идемпотентно
   повторяется), после неё — случился необратимо. Имена ревизий
   детерминированы (`spec-r{N+1}`), поэтому `superseded_by` вправе ссылаться
   на ещё не материализованную ревизию — но только пока висит её
   `create_session` в `next_action` либо после материализации; сошедшаяся
   spec-rN сохраняет `outcome: converged` — перекрытие выражается только
   `superseded_by` (P3);
5. **новая ревизия**: исполнить `create_session` для spec-rN+1; окончательный
   провал создания (после ретраев resume) → `FAILED`, записанный commit
   возврата остаётся в истории как зафиксированное намерение.

Падение между durable-записью ревью (шаг 0, сторона сессии) и записью
pipeline-intent (шаг 2) покрыто reconciliation: при resume runner заново
инспектирует последний раунд активной pair-сессии, заново обнаруживает дефект
и приходит к тому же `operation_id`. Падение на любом последующем шаге
допроигрывается по `next_action` (§4.3). Каждый шаг — предмет crash-тестов
(§10).

Контекст spec-rN+1: снапшот task + текущая спека (файлы на диске — источник
истины; после cleanup шага 3 это последняя **принятая** версия пары) +
архитектурные находки pair-ревью. Находки попадают в prompt как
**недоверенные структурированные данные** в тегах «данные, не инструкции» —
тот же барьер, что у текста автора перед ревьюером (SPEC-001 §7). Автор
spec-rN+1 меняет только спеку (`doc-scope`); новая pair-rN+1 заново создаёт
или перерабатывает план от последней принятой версии, стартует без carried
issues прежней и без унаследованных approve/checklist: полная перепроверка
пары (P5).

## 8. Resume и экспорт

### 8.1 Resume

Порядок `disp pipeline resume` строгий — reconciliation имеет приоритет и
над сохранённой фазой сессии, и над replay intent'а, потому что после
`CONTINUE` write-ahead сессии уже указывает на следующий `PROPOSING`, и
session-resume, запущенный первым, продолжил бы сессию, которую надлежит
припарковать:

0. **P9-сверка** по **последней записи анкера** — файл находится по
   `<anchor_root>` из живой конфигурации (`--config`, иначе дефолтный
   поиск конфига: снапшот в каталоге пайплайна для этого не годится, он
   в недоверенном дереве) и `<anchor_id>` = `--slug`; оба входа вне
   рабочего дерева. Identity берётся из самой записи, а не из манифеста.
   Делается до чтения манифеста и артефактов сессии, которые могли быть
   подменены. Сверка применяется, **только если последняя запись —
   `pre_turn`** (ход прерван на середине); `turn_completed` или пустой
   **существующий** журнал означают, что сверять нечего — штатные записи
   runtime после успешного хода подменой не являются. **Отсутствие файла
   анкера — отказ, а не пропуск**: иначе пайплайн с нестандартным
   `anchor_path` при `resume` без того же конфига смотрел бы в дефолтный
   журнал, не находил записей и молча пропускал сверку. Ложным этот отказ
   не бывает: `run` создаёт пустой анкер первым действием (§3.1), так что
   отсутствие файла означает неверное расположение, а не раннюю стадию;
1. **чтение манифеста**; сессии с `outcome ≠ null` или `superseded_by ≠
   null` не возобновляются никогда;
2. **read-only обнаружение**: инспекция последнего durable-раунда активной
   pair-сессии на архитектурный дефект (§7.3 шаг 1) — только вычисление
   вердикта и `operation_id`, **никаких мутаций** (ни манифеста, ни
   worktree); session-resume при обнаруженном дефекте не вызывается;
3. **сверка worktree** (модель ниже) — сама по себе немутирующая: она не
   вправе трогать даже индекс (канонический дифф берётся поверх
   одноразового индекса, а не через `add --intent-to-add` рабочего) —
   и предшествует **любому** мутирующему шагу:
   и replay `next_action`, и возврат §7.3 несут destructive reset, который
   поверх непроверенного дерева уничтожил бы внешнюю правку;
4. **мутирующая фаза** — только после чистой/атрибутированной сверки либо
   явной санкции оператора: replay незавершённого `next_action` (§4.3)
   и/или исполнение возврата §7.3 (шаги 2–5) по вердикту шага 2;
5. session-resume действительно активной сессии, с установленной
   `RoundBoundaryPolicy` (§7.1).

**Модель внешней правки.** Пара «хеши документов + git HEAD» не отличает
легальную работу упавшего шага от ручной правки, а автоматический `git
reset` перед re-run `PROPOSING` уничтожил бы ручную правку раньше, чем её
можно заметить. Поэтому правило: **resume никогда не выполняет destructive
reset поверх состояния, происхождение которого не доказано**:

- HEAD совпадает с записанным, дерево чистое → продолжать;
- dirty diff **байт-в-байт сводится** к записанному `changes.patch` (окно
  «proposal записан, раунд не принят») → легален, продолжать;
- всё остальное — включая dirty state в окне in-flight `PROPOSING`, где
  происхождение байтов неразличимо в принципе, — resume останавливается,
  показывает диф и требует явного выбора человека: `--discard-round`
  (санкционировать reset и переиграть раунд; ручные правки при этом
  сознательно теряются — это записанное решение оператора, не молчание
  инструмента) либо `--adopt-external` (принять правку как внешнюю и уйти
  в новую ревизию; семантика обоих флагов — §3.1). Reset SPEC-001 перед
  re-run `PROPOSING` исполняется только после этой санкции. Между сессиями
  (активной нет) ожидаемое состояние — последний принятый коммит, и любой
  dirty diff требует того же явного выбора.

### 8.2 Экспорт: готовая к публикации пара

Цель v1 — не «сам открывает draft-PR», а **«выдаёт полностью готовую к
публикации пару одним draft-PR»**. Экспорт идемпотентен, байты канонические
(сортированные ключи, без времени экспорта; повтор — байт-в-байт). Публикация
(push, `gh pr create`) — внешний эффект, исполняет человек. Состав `result/`:

- `manifest.json` — честная сводка: `converged: bool`, фазы, сессии с
  outcome/superseded_by, хеши артефактов, task и чеклистов, агрегированный
  бюджет, открытые находки при эскалации, причина эскалации;
- `pr_title.txt`, `pr_body.md` — сводка вердиктов и evidence по чеклистам,
  история контуров;
- `publish.txt` — команды `git push` + `gh pr create --draft` с фактически
  определёнными remote/branch и корректным shell quoting; если remote или
  GitHub-репозиторий однозначно не определяются локально — параметризованный
  шаблон с явным предупреждением, а не придуманная команда.

Консистентность всего набора: файлы содержимого пишутся атомарно пофайлово,
`manifest.json` — **последним, как commit marker**; он перечисляет полный
ожидаемый набор файлов результата с их sha256. Экспорт начинается с удаления
из `result/` файлов, не входящих в новый набор (stale-остатки прежнего
partial/full экспорта не переживают повтор); читатель считает экспорт
валидным только при совпадении набора и хешей с манифестом — смесь старых и
новых файлов после падения распознаётся, а не сходит за результат.

CLI-коды: `DONE` после сходимости — 0; `ESCALATED` — ненулевой; `FAILED` —
ненулевой, экспорт только явным `export --partial`.

## 10. Требования к тестированию

Существующие паттерны suite (fake-адаптеры, fixture-репо). Обязательный
минимум:

- unit: схема манифеста; закрытая таблица переходов (включая отсутствие
  рёбер из `DONE`); резолв и идемпотентность каждого `kind` у `next_action`;
  интерпретация терминалов по durable-состоянию; неизменяемость `outcome` +
  `superseded_by`; идемпотентность `FAILED → FAILED` (P8) — без дубликата
  transition в манифесте; попытка отключить baseline-гейт в конфиге — отказ
  валидации конфига; v2-reader принимает артефакты v1; пересчёт
  `budget_used` без двойного начисления при повторном `run_session`;
- контракт `artifact_root`: default `artifact_root = workspace_root` даёт
  байт-в-байт текущее поведение; две сессии под разными `artifact_root`
  одного `workspace_root` не конфликтуют за `session.json`;
- `RoundBoundaryPolicy`: без политики `drive()` ведёт себя как сегодня
  (байт-в-байт); `park` возвращает управление до исполнения шага следующей
  фазы; припаркованная сессия не возобновляется resume'ом (§8.1 шаги 1–2 —
  приоритет reconciliation над сохранённой фазой сессии);
- P9: запись автора в control-plane файл (манифест, артефакт раунда,
  усечение event log) → `FAILED (invariant_violation)`; легальный append
  оркестратора в журнал проходит prefix-property; kill во время хода автора
  → resume ловит подмену по анкеру до чтения артефактов; **подмена
  манифеста ловится анкером** — сценарий, ради которого анкер вынесен из
  дерева: манифест автору достижим, анкер нет, и снапшота в манифесте не
  существует, подделывать нечего; повторный append той же записи после
  краха идемпотентен и подменой не считается; `anchor_path` внутри
  `workspace_root` → отказ старта; адаптер без `path_write_deny`
  допускается и не роняет старт; **посторонний untracked-файл вне
  `.disputatio/` отвергается предусловием `run`** — негативный сценарий
  «файл пережил старт и был уничтожен первым `PROPOSING`» невозможен по
  построению, а собственный untracked под `.disputatio/` (другой пайплайн)
  старт не блокирует;
- atomic chaining `next_action`: commit возврата заменяет intent преемником
  в одной записи, `predecessor_operation_id` сохранён; resume после падения
  на chained-intent'е допроигрывает преемника без повтора предшественника;
- порядок resume: обнаруженный дефект при грязном неатрибутируемом дереве →
  остановка ДО каких-либо мутаций (ни reset §7.3, ни replay); `--adopt-external`
  паркует сессию (`abandoned`) и открывает новую ревизию, решение записано в
  `operator_decisions`; принятая правка переживает первый `PROPOSING` новой
  ревизии (base_commit = операторский чекпоинт) и resume; при обнаруженном
  архитектурном дефекте adopt не обходит P6 — после чекпоинта исполняется
  возврат в spec-ревизию;
- adoption fail-closed: диф с путём (tracked или untracked) вне
  `spec_path`/`plan_path` — отказ целиком; новый untracked документ по
  `spec_path`/`plan_path` принят и входит в чекпоинт; правка `spec_path` в
  pair-контуре → spec-ревизия даже без architectural finding (reason
  `external_spec_adopt`, outcome ровно один — `abandoned`, `record_return`
  не вызывается); crash-тесты интента `adopt_external` на каждом шаге
  (после записи patch-файла, после git-чекпоинта до commit point) — resume
  находит чекпоинт по trailer'у и не создаёт второй коммит; падение
  `discard_round` между reset'ом и записью решения не теряет provenance;
- `SessionLifecyclePolicy`: default no-op — `drive()` байт-в-байт как
  сегодня; before/after вызываются на каждом `PROPOSING`, ошибка политики →
  `FAILED`;
- doc-гейты на fixture-репо: битые ссылки/якоря/пути, дрейф строк и якорного
  текста, symlink-escape, Unicode- и повторяющиеся заголовки, неоднозначные
  формы → warning, не fail (кейсы по мотивам bench-verify);
- валидация: property-тесты V1–V5, V7–V8 («approve не проходит при
  fail/неполном чеклисте», «approve при blocker/major issue → отказ»,
  «S1: pass при blocker/major → отказ», «blocker/major в pair без
  defect_class → retry», связность `issue_ids` и их severity, evidence
  непуст при любом статусе);
- интеграционные:
  - сквозной прогон двух контуров со скриптованными артефактами до экспорта;
  - архитектурный возврат: смешанное ревью (architectural + execution) →
    приоритет architectural (P6);
  - pair-rN+1 после возврата проверяет пару заново: никакого унаследованного
    approve/checklist/carried issues (P5);
  - crash recovery на **каждом** шаге возврата §7.3, включая падение между
    durable-записью ревью и записью pipeline-intent (reconciliation даёт тот
    же `operation_id`, дубликата возврата нет), идемпотентность cleanup
    worktree (повтор reset — no-op) и пару «каталог сессии создан,
    `session_started` не записан» — resume без дубликатов;
  - внешняя правка документа → resume останавливается; dirty diff,
    байт-в-байт сводящийся к записанному `changes.patch`, легален; dirty
    state неатрибутируемого происхождения (включая in-flight `PROPOSING`) —
    остановка без destructive reset, reset только после явного
    `--discard-round` (§8.1);
  - экспорт: `manifest.json` как commit marker — падение до него оставляет
    невалидный по манифесту набор, повтор экспорта убирает stale-файлы и
    даёт байт-в-байт результат (§8.2);
  - анти-сикофантия раунда 1 для `Mode.DOCUMENT`: правка документа не даёт
    немедленной сходимости без содержательного цикла ревью;
  - V6: до `decide()` не доживает approve, нарушающий чеклист —
    интеграционная гарантия, что `core/deciding.py` не потребовал правок.

## 11. Вне v1 / открытые вопросы

- Автоматическая публикация draft-PR — отдельный адаптер/команда поверх
  стабильного контракта экспорта; FSM и документный пайплайн не меняются.
- Детерминированный гейт трассируемости спека→план — после проектирования
  REQ-id-конвенции; подключается как обычный doc-гейт.
- Жёсткие пайплайн-лимиты бюджета (проверка между раундами).
- Обобщение до N-stage пайплайна — только при появлении второго реального
  потребителя; его требования дадут основания для модели вместо угадывания.
- discovery-стадия перед спекой (правило помечает её опциональной) — вне v1.
- Изоляция уровня ОС для автора (контейнер/mount namespace/сэндбокс), при
  которой control plane физически недостижим произвольным shell'ом. В v1
  P9 честно обещает обнаружение, а не предотвращение (P9, модель угроз).
- Erratum SPEC-001 §2/§5.5: выровнять нормативный текст про `ESCALATED` с
  фактической семантикой реализации (резолюция пользователя — после DONE,
  интерактивного шага в сессии нет) — отдельным изменением SPEC-001, не
  частью SPEC-002 (§7.2).
