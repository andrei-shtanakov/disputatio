# Трекаемая TDD-evidence

Каталог заполняется автоматически. `scripts/tdd_evidence_export.py` вызывается
плагином `spec/plugins/tdd-evidence/` на hook-точке `post_review` spec-runner'а
(≥ 2.35.0) и пишет сюда `<namespace>/<TASK>.json` по схеме
`disputatio/tdd-evidence/v1`.

- **Что доказывает файл:** цепочку RED → GREEN → review для одной задачи —
  подтверждённый red-чекпоинт, claims его линии, достигнутые фазы (включая
  `refactoring`), вердикты гейтов `tdd.red`/`tdd.claims`/`review`. Неполная
  цепочка не материализуется: экспортёр отказывается и называет недостающее.
- **Вердикт `review` требует `review_policy: required`.** Под дефолтным
  `advisory` гейт ревью не регистрируется вовсе, вердикта не существует, и
  экспортёр отказывает — как и произошло в первом прогоне 2026-08-22. Политика
  объявлена в `project.yaml`; менять её задним числом нельзя без нового
  прогона: `review_policy` входит в `POLICY_KEYS`, и прежние вердикты
  протухают вместе с `config_hash`.
- **Имя каталога** — `ws-<workstream-id>`, выведённое из ветки `ws/<id>`
  (INV-16); сырой неймспейс живой БД лежит внутри файла как `state_namespace`.
  Вне workstream'а имя берётся из БД и выглядит как хеш.
- **`blob_sha` — снимок момента, а не запрет на эволюцию.** Claim фиксирует
  байты тест-файла на момент прогона; позже файл живёт обычной жизнью — его
  правят, рефакторят, переносят. Расхождение записанного `blob_sha` с текущим
  содержимым файла не делает артефакт недействительным: он утверждает, что на
  момент задачи red был подтверждён именно этими байтами. Что действительно
  запрещено — править файл, **пока** claim активен: это ловит claims-гейт.
- **Руками не править.** Путь входит в `harness_files` при
  `harness_guard: strict`: правка агентом валит попытку до гейтов. Артефакт
  ценен ровно тем, что его написал не тот, кого он аттестует.

Почему в репо, а не только в состоянии прогона: evidence здесь — продукт
сертификационной ступени, а не лог. В git она мержится вместе с работой, видна
в ревью диффом и реплицируется каждым клоном; в операторском `db_dir` она
лежала бы в единственном экземпляре с ротацией. Обоснование целиком —
`docs/plans/2026-08-21-tdd-gate-migration-assessment.md` §5.1.
