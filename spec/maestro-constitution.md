# Constitution — disputatio, волна 1

## TDD-дисциплина (обязательна для каждой leaf-задачи)

1. Сначала тест: выбери МИНИМАЛЬНЫЙ тест, доказывающий новое поведение задачи.
   Regression-тест фиксирует наблюдаемое поведение; speculative-тест на
   несуществующие требования не пиши.
2. До реализации выполни: `uv run python scripts/tdd_gate.py red --node-id
   <tests/file.py::test_name>` — гейт проверит, что тест падает именно
   assertion'ом, и создаст red-чекпоинт. Без подтверждённого red задача НЕ
   завершится (test_command упадёт).
3. Форматируй тест ДО `red` (`uv run ruff format <файл>`); ПОСЛЕ `red` НЕ
   запускай `ruff format`/`ruff check --fix` по `tests/**` — тест обязан
   остаться байт-в-байт таким же, каким был на red-чекпоинте, иначе задача
   запирается (`verify` отвергает изменённый тест — см. п.6).
4. Только затем пиши реализацию. Менять assertion ради зелёного ЗАПРЕЩЕНО.
   Если тест оказался неверным — самостоятельный перезапуск `red` для уже
   зафиксированной задачи агенту недоступен (v1: supersession запрещена).
   Исправление требует вмешательства оператора — снять claim/verdict
   задачи или выдать waiver — только после этого возможен новый честный
   red-цикл. Объясни ситуацию в отчёте и остановись, не пытайся обойти
   гейт правкой теста без нового red.
5. `scripts/tdd_gate.py`, `spec/plugins/`, `spec/.tdd-evidence/verdicts/`,
   `spec/.tdd-evidence/waivers/` — НЕ редактировать (harness; правки блокируют
   задачу).
6. Гейт и полный suite запускаются автоматически после задачи; локально можно
   проверить себя: `uv run pytest -q`. Сам `tdd_gate.py verify` руками не
   гонять — это harness_guard-ловушка (verify пишет verdict в
   `spec/.tdd-evidence/verdicts/`, а этот путь harness-owned).
