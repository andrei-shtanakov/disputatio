# Constitution — disputatio

## TDD-дисциплина (штатный режим spec-runner, `execution_mode: tdd`)

Кто это читает: **пас реализации (GREEN) и ревьюер** — spec-runner подставляет
конституцию в их промпты (`prompt._render_task_prompt`, `review.py`).
**RED-пас её не получает**: его промпт собирается кодом spec-runner
(`prompt.build_red_prompt`) и конституцией не расширяется. Поэтому здесь нет
инструкций для автора падающего теста — правила, написанные тому, кто их не
прочтёт, создают ложное чувство покрытия. Описание цикла в п.1 нужно, чтобы
ревьюер понимал, что именно он проверяет.

1. **Как устроен цикл.** Падающий тест пишет отдельный RED-пас: один тест, без
   реализации, в НОВОМ файле, которого не было на baseline. Его коммит
   реплеится в одноразовом worktree, и только подтверждённый red открывает
   переход `red_verifying → green_implementing`. К моменту твоей работы тест
   уже существует, зафиксирован чекпоинтом и залочен побайтно.
2. **Залоченные файлы не редактировать.** Их полный список приходит блоком
   frozen files в конце твоего промпта. Лок покрывает ВСЕ активные claim'ы
   неймспейса, а не только файл твоей задачи: правка чужого залоченного теста —
   такое же нарушение, даже если выглядит безобидной (аннотация типа,
   переформатирование). Ловится claims-гейтом и стоит отклонённого кандидата
   вместе с уже оплаченным пасом.
3. **Менять assertion ради зелёного ЗАПРЕЩЕНО.** Если тест неверен — остановись
   и объясни ситуацию в отчёте, не обходи лок правкой теста. У оператора для
   этого есть типизированные команды: `spec-runner tdd abandon` (этот red
   негоден, коммит остаётся в истории, разрешён новый честный цикл),
   `spec-runner tdd repair` (правка залоченного файла законна, открывается новая
   родословная), `spec-runner tdd resume` (зелёное достигнуто — вернуть
   подтверждённый red и его claim'ы), `spec-runner tdd release` (задача
   завершена — снять локи).
4. **Harness не редактировать.** `scripts/tdd_evidence_export.py`,
   `spec/plugins/**`, `spec/evidence/**`, `scripts/tdd_gate.py`,
   `spec/.tdd-evidence/verdicts/`, `spec/.tdd-evidence/waivers/` и этот файл.
   `harness_guard: strict` валит попытку ДО гейтов, а сообщение уходит в промпт
   следующей попытки. Сам штатный TDD-гейт правкой недоступен по построению —
   это код установленного пакета, а не файл репо.
5. **Evidence пишется автоматически, руками — никогда.**
   `spec/evidence/<ns>/<TASK>.json` создаёт экспортёр на точке `post_review`:
   после вердикта ревью, до коммита задачи, так что артефакт уезжает в той же
   доставляемой истории, что и работа. Артефакт доказывает цепочку
   RED → GREEN → review; написанный агентом JSON доказывает только то, что агент
   умеет писать JSON. Неполная цепочка не материализуется — экспортёр отказывает
   и печатает недостающее.
6. **Проверить себя локально:** `uv run pytest -q`. Полный suite и линт после
   задачи гонит spec-runner сам; `tdd_evidence_export.py` руками не запускать —
   это harness-путь (п.4), у него своя точка вызова.
