## Категории выхода

| Категория | Значение |
|---|---|
| `OK` | команда завершилась ожидаемо успешно |
| `WARN` | проверка не прошла, но не блокирует фазу |
| `EXPECTED_FAIL` | команда упала именно так, как предписано (assertion выбранного теста) |
| `UNEXPECTED_FAIL` | упало не то или не так (чужие тесты, другой участок) |
| `ERROR` | команда не смогла отработать (import/collection error, окружение) |

Вердикт фазы: все проверки с `blocking = yes` (колонка «Проверки») дают `OK`
(или предписанный `EXPECTED_FAIL` внутри D0-MUT-01); проверки с
`blocking = no` (сейчас D0-GIT-04 и D0-TEST-02) могут быть `WARN` без срыва
вердикта. Любые `WARN` перечисляются в транскрипте явно. Определение вердикта
фазы опирается на колонку `blocking`, а не на прозу.

## Проверки

Формат: `check_id | precondition | command | expected | blocking | categories | remediation`.
Все команды исполняются из корня репо.

Принцип: exit code фиксируется у проверяемой команды, не у последнего
элемента пайпа; пайпы в поле `command` запрещены (или только с явным
`pipefail`).

Принцип (редакция 4): **«git чист» не значит «окружение чисто»**. Проверки
git-состояния говорят о трекаемых файлах и ни о чём больше; кэш байткода,
`.venv` и прочее окружение ими не покрыты. Всюду, где протокол доказывает
восстановление, доказательством служит повторный прогон инструмента, а не
чистый `git status`.

|---|---|---|---|---|---|---|

## D0-MUT-01 — mutation_probe (оракул обязан уметь падать)

Precondition: D0-GIT-05 = OK, D0-TEST-03 = OK. Селектор пробы:
`tests/test_smoke.py::test_package_importable`.

Связанность: текст `tests/test_smoke.py` и шаг 2 D0-MUT-01 связаны литералом
`0.1.0`: рефакторинг теста обязан обновить шаг 2, иначе проба тихо
расстыкуется. Следствие: в докстринге теста литерала `0.1.0` быть не должно
— мутация `replace` не должна задевать докстринг.

| шаг | command | expected |
|---|---|---|
| 1. зафиксировать базу | `git rev-parse HEAD` → записать SHA; `git status --porcelain` → пусто | OK |
| 2. сломать assertion | `python3 -c "import pathlib; p = pathlib.Path('tests/test_smoke.py'); p.write_text(p.read_text().replace('0.1.0', '9.9.9'))"` | exit 0; доказательство мутации — `git diff --quiet tests/test_smoke.py` завершается exit 1 (файл изменён); «exit 0 самой мутации» больше не является доказательством |
| 3. подтвердить красный | `uv run pytest -q tests/test_smoke.py::test_package_importable` | exit 1, в выводе `AssertionError` → **EXPECTED_FAIL**; exit ≥2 или падение другого теста → провал пробы (ERROR/UNEXPECTED_FAIL) |
| 4. тикнуть mtime-секунду | `python3 -c "import time; time.sleep(1.1)"` | exit 0; обоснование — ниже, шаг обязателен и пропуску не подлежит |
| 5. восстановить | `git checkout -- tests/test_smoke.py` | exit 0 |
| 6. проверить восстановление в git | `git rev-parse HEAD` == SHA из шага 1 **и** `git status --porcelain` пуст | OK; иначе — провал пробы. Говорит только о трекаемых файлах |
| 7. подтвердить зелёный без сброса кэша | `uv run pytest -q tests/test_smoke.py::test_package_importable`, при этом между шагами 2–7 не было **ручной** очистки или инвалидации `__pycache__` (запись кэша самим pytest на шагах 3 и 7 — нормальный ход пробы, а не нарушение) | exit 0 → OK; ненулевой exit → **не провал сразу**, а диагностика ниже |

### Почему шаг 4 существует

Мутация `0.1.0` → `9.9.9` **не меняет размер файла** — это свойство самой
пробы, а не случайность. Заголовок `.pyc` хранит mtime исходника с точностью
до секунды и его размер; если мутация (шаг 2) и восстановление (шаг 5)
уложились в одну mtime-секунду, оба поля совпадают, и кэш, скомпилированный на
шаге 3 из **мутированного** исходника, считается актуальным. Шаг 7 тогда даёт
ложный красный, а дерево при этом git-чистое.

Это не гипотеза: воспроизведено в D5 (`D0-transcript-integration-2026-08-17.md`,
прогон 1), root cause доказан цепочкой RC-0…RC-3 — удаление одного файла
`tests/__pycache__/test_smoke.cpython-312-pytest-9.1.1.pyc`, без единой правки
трекаемых файлов, возвращало зелёный.

Шаг 4 ставится **между шагами 2 и 5** и нигде иначе: `.pyc` пишется на шаге 3
и записывает mtime, выставленный шагом 2, поэтому расходиться должны именно
эти два значения.

### Диагностика красного шага 7

Красный шаг 7 не различает «восстановление не сработало» и «окружение было
грязным», поэтому редакция 4 требует различить их явно, а не перезапускать
пробу наугад:

| шаг | command | вывод |
|---|---|---|
| D-1 | удалить **только** кэш целевого теста: `python3 -c "import pathlib; [f.unlink() for f in pathlib.Path('tests/__pycache__').glob('test_smoke.*.pyc')]"` | трекаемые файлы не трогаются |
| D-2 | `uv run pytest -q tests/test_smoke.py::test_package_importable` | exit 0 ⇒ причина в кэше; exit 1 ⇒ причина в дереве; exit ≥ 2 ⇒ причина в инструменте |

- **exit 0 на D-2** — проба **недействительна**, категория `ERROR`, а не
  `UNEXPECTED_FAIL`: оракул не опровергнут, грязным было окружение. Проба
  перепрогоняется начисто, и транскрипт обязан содержать **обе** попытки —
  неудачную с диагностикой и каноническую.
- **exit 1 на D-2** — восстановление действительно не сработало: провал пробы.
- **exit ≥ 2 на D-2** — упал сам инструмент (collection/import error), а не
  проверяемый тест: категория `ERROR`, проба **недействительна**, но по другой
  причине, чем stale-кэш. Так же, как на шаге 3, `exit ≥ 2` никогда не читается
  как «тест не прошёл»: об оракуле это не говорит ничего. Чинится окружение,
  затем проба прогоняется начисто.

Phase-заметки: в `phase=integration` (D5) шаги идентичны; дополнительно
требуется совпадение HEAD и dirty-state после восстановления (шаг 6 —
blocking) и прогон на интеграционной ветке, а не на `d0-baseline`.

## Формат транскрипта

Файл `docs/plans/D0-transcript-<phase>-<YYYY-MM-DD>.md`. На каждую проверку —
строка таблицы: `check_id | команда как выполнена | exit code | категория |
заметка`, плюс fenced-блок с сырым выводом для D0-TEST-03, D0-TYPE-01 и всех
шагов D0-MUT-01. В конце — вердикт фазы и список WARN.
