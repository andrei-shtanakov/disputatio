# Оценка миграции локального TDD-гейта на штатный `execution_mode: tdd`

> Дата: 2026-08-21. Статус: **оценка, не миграция** — решение принимается по её
> итогам (пункт `todo://disputatio/tdd-gate-migration-assessment`).
> Оцениваемая сторона: spec-runner **2.34.0** (установленная версия сверена с
> `spec-runner --version`), контракт TDD отгружен по D7-A / spec-runner#141.

## 1. Почему вопрос возник

`scripts/tdd_gate.py` (1997 строк) и плагин `spec/plugins/tdd-gate` писались в
D4 потому, что у spec-runner не было фаз: задаче негде было хранить факт «тест
написан и подтверждённо падает». Дизайн-док соседа формулирует ровно этот
дефицит как причину принять наш запрос:

> A task has no phases, so "the test is written and confirmed failing" has
> nowhere to live except bespoke evidence files on disk.

Дефицит закрыт: срезы 0–4a отгружены, `execution_mode: standard|tdd` —
штатный контракт. Значит, наш гейт из «единственного способа» превратился в
«дубль штатного», и держать 1997 строк харнеса без пересмотра — решение,
которое надо принять заново, а не унаследовать.

## 2. Что измерялось

| Сторона | Источник |
|---|---|
| Наш гейт | `scripts/tdd_gate.py`, `spec/plugins/tdd-gate/plugin.yaml`, `spec/maestro-constitution.md`, `project.yaml` (блок `spec_runner`) |
| Штатный контракт | `spec-runner/docs/state-schema.md` §§ `phase_results`/`gate_verdicts`/`red_checkpoints`/`tdd_claims`/`tdd_remedies`/`agent_calls`/`tdd_phases`, `src/spec_runner/{config,tdd,tdd_runners,gates,claims}.py`, `spec-runner tdd --help`, README §Configuration |
| Стык с Maestro | `maestro/models.py` (`SpecRunnerConfig.to_executor_config`, `extra_executor_config`, `PostmortemConfig`), `maestro/orchestrator.py` (`_postmortem_secured`, `_postmortem_root`), `maestro/postmortem.py`, `maestro/workspace.py` |

Объём нашей evidence-базы на момент оценки: **100 claims, 102 verdicts,
6 waivers** в семи неймспейсах (`ws-w-contracts`, `ws-w-fsm`, `ws-w-verifier`,
`ws-w-adapters`, `ws-w-context`, `ws-w-events`, `ws-w-runtime`), **234 коммита**
трогают `spec/.tdd-evidence/`. Тесты харнеса — 130 в `tests/harness/`
(2725 строк).

## 3. Соответствие механизмов: покрывается штатно

| Наш механизм | Штатный аналог | Оценка |
|---|---|---|
| `Claim` (red SHA + baseline + селектор + blob-лок теста) | `red_checkpoints` (`commit_sha`, `baseline_sha`, `selector`, `environment_id`, `execution_mode`, `config_hash`) + `tdd_claims` (`path`, `blob_sha`, `status`) | **Покрыт с запасом.** Разложено на две таблицы: claims запрашиваются по `(namespace, status, path)` межзадачно — у нас это разбирается перебором файлов (`locked_test_drift`) |
| Неймспейс `ws-<id>` из ветки (INV-16) | Колонка `namespace`, чтение по `(task_id, namespace)` | **Покрыт**, причина названа та же: одинаковые `TASK-NNN` из разных workstream-ов сталкиваются, когда ветки сходятся |
| Байт-лок теста | `blob_sha` над сырыми байтами, без нормализации переводов строк | **Покрыт**, формулировка соседа буквально наша |
| Независимый replay red-SHA в одноразовом worktree | `git worktree add --detach <sha>` + `prune` в `tdd.py` | **Покрыт механически** (оговорка про независимость — §5.3) |
| Вердикты `PASS`/`EXPECTED_FAIL`/`UNEXPECTED_FAIL`/`ERROR` | `RedOutcome` (`expected_fail`/`not_red`/`unverifiable`) + `PhaseOutcome` (шесть значений) | **Покрыт с уточнением**: разделение «тест проходит» (факт о коде) и «выяснить не удалось» (факт о нас) — то же, что наш `ERROR` vs `UNEXPECTED_FAIL` |
| `WAIVED` как пятый вердикт | `phase_waivers` — решение оператора с `actor`, `reason`, `provenance`, рядом с сохранённым наблюдением | **Покрыт лучше нашего.** Правка принята ещё при приёме #141: waiver — не исход. Наш `WAIVED != PASS` был приближением к той же мысли |
| `abandon` / `repair` | `tdd_remedies` (`operation`, `actor`, `reason`, `new_checkpoint_id`) + статусы `active`/`superseded`/`abandoned` | **Покрыт**, имена команд совпадают |
| Recovery claim из трейлеров red-коммита | `checkpoint_id` как производный хеш, переживающий пересборку состояния | **Покрыт иначе, эквивалентно по цели** |
| Плагин `post_done` → `audit` (фоллбэк «у DONE есть вердикт») | RED-гейт: переход в GREEN без подтверждённого red отказан; `tdd_phases` пишет и отказы (`refused:<target>`) | **Покрыт строго сильнее** — см. §4.1 |

## 4. Что штатный контракт даёт сверх нашего

### 4.1 Точка отказа сдвинута до реализации

Наш primary edge — `test_command: "tdd_gate.py verify && uv run pytest -q"`,
то есть стадия `tests`, до `commit`. Это уже не post-hoc, но отказ наступает,
когда реализация **уже написана**: гейт может только не выпустить задачу.
Плагин `post_done` — фоллбэк ещё позже, после коммита (известный вход D4).

Штатный RED-гейт отказывает **на переходе `red_verifying → green_implementing`**:
без подтверждённого red пас реализации не запускается вовсе. Это ровно тот
blocking finding, который волна записала в D7-A, и он закрыт не нами.

### 4.2 Учёт денег

`agent_calls` — по строке на вызов, `cost_usd` **nullable, и NULL ≠ 0**:
ревьюер, убитый таймаутом, был оплачен, и `0.0` сделал бы его неотличимым от
дешёвого вызова. `unmeasured_calls()` публикует число неизмеренных. У нашего
гейта учёта нет вообще — деньги за red-пас были невидимы.

### 4.3 Пиновка политики

`gate_verdicts` ключуется на `(task_id, gate_id, checkpoint_sha, config_hash)`,
где `config_hash` считается **только** по `POLICY_KEYS` (`execution_mode`,
`review_policy`, `tdd_runner`, …). Вердикт — утверждение о конкретном дереве
под конкретной политикой, и он протухает при смене любой из двух. У нас
эквивалента нет: сменить политику и унаследовать старые вердикты можно молча.

### 4.4 Двери, которых у нас нет

`tdd resume` (восстановить подтверждённый red вместе с claims одной
транзакцией после green) и `tdd release` (снять локи при завершении задачи).
Именно их отсутствие у нас породило бэклог-пункт
`todo://disputatio/tdd-gate-red-supersede` — то есть этот пункт с большой
вероятностью закрывается миграцией, а не собственной разработкой.

### 4.5 Иммунитет харнеса

Наш гейт — файл в репо, который агент физически может отредактировать; защита
держится на `harness_guard: strict` + перечислении путей в `harness_files`
(включая саму конституцию — правка N2 волны). Штатный гейт — код
установленного пакета: агенту его править нечем. Это снимает целый класс
обхода, а не усложняет его.

## 5. Что теряется

### 5.1 Evidence перестаёт быть артефактом репо — главная потеря

Сначала снятое обвинение, чтобы не пугать несуществующим: **evidence не
уничтожается**. Штатная evidence живёт в SQLite `.executor-state.db` внутри
worktree, но Maestro перед уборкой копирует её в post-mortem архив
(`maestro/postmortem.py`, `capture_archive` — БД + логи харнеса), и уборка
worktree выполняется **только** если архив на месте:

```python
if await self._postmortem_secured(workstream_id):
    self._workspace_mgr.cleanup_workspace(workstream_id)
```

Причём выключить захват нельзя по построению: в `PostmortemConfig` намеренно
нет ключа `enabled` — «a config switch that turns it off would recreate the
incident with one line of YAML». Отсутствие блока `postmortem:` (наш случай)
означает дефолты, а не «выключено».

Разница, которая остаётся после этой поправки, — не в живучести, а в **классе
артефакта**:

| | Наша evidence | Штатная + архив |
|---|---|---|
| Где | `spec/.tdd-evidence/**` в репо | `<db_dir>/postmortem/<ws>/…` вне репо |
| Кто хранит | git | ФС операторской машины |
| Едет в master с PR | да | нет |
| Видна в ревью как диff | да | нет |
| Retention | история git (234 коммита) | `keep_per_workstream: 5`, логи обрезаются по 64 MiB |
| Переживает снос воркспейса | да | нет |
| Формат | JSON, читается глазами и грепом | SQLite-снимок + логи |

То есть цепочка claim→verdict, ради которой существует ось H3 («≥1 leaf-задача
с полной evidence-цепочкой»), перестаёт быть частью того, что мы мержим и
показываем, и становится машинно-локальным диагностическим архивом с
ротацией. Для обычного проекта это ровно правильный размен: состояние прогона —
расходный материал, и держать его в git незачем. Для сертификационной ступени
evidence — продукт, а не лог, и размен обратный.

### 5.2 Работа без продуктовых зависимостей

Наш гейт — stdlib-only и по построению: он запускается из `test_command` до
установки зависимостей проекта. Штатный — внутри исполнителя. Для greenfield
(вход D7-B) это разница; для сегодняшнего disputatio — нет.

### 5.3 Независимость судьи

Наш гейт — третья сторона и агенту, и исполнителю: replay делает отдельный
процесс, не участвующий в оркестрации. Штатный replay — код самого
исполнителя. Механически проверка та же (§3), но «независимость» в смысле
пилота слабеет: судья и организатор прогона — одна программа. Для обычного
проекта это не важно; для стенда, чья задача — доказывать дисциплину, это
предмет отдельного решения, а не деталь.

### 5.4 Цена в вызовах

У нас red пишет агент в своём обычном пасе и сам зовёт `tdd_gate.py red`
(конституция, п. 2) — дополнительного оплаченного вызова нет. Штатный режим
делает **три** оплаченных вызова на попытку: RED authoring, GREEN
implementation, review. Разделение чище и даёт `agent_calls`-леджер, но за
него платят.

### 5.5 Экспериментальный статус контракта

Каждая TDD-таблица в `state-schema.md` помечена *experimental: shape may change
… external consumers should not depend on it yet*. Строя сертификационную
evidence на них, мы становимся именно таким внешним потребителем.

## 6. Во что обходится переход

**Чего НЕ требуется** (проверено, а не предположено):

- правок в maestro: `SpecRunnerConfig.extra_executor_config` — произвольный
  оверлей с deep-merge поверх сгенерированного конфига, а spec-runner читает
  legacy-обёртку (`executor_config = data.get("executor", data)`). Значит
  `execution_mode: tdd` и `tdd_runner: pytest` кладутся туда же, где у нас уже
  лежат `on_task_failure` и `harness_guard`;
- обновления spec-runner: установлен 2.34.0, контракт в нём есть;
- кросс-репных issue: ни одной. Переход целиком в границах нашего репо.

**Что требуется:**

1. `project.yaml` — `extra_executor_config.executor.execution_mode: tdd`,
   `tdd_runner: pytest`; `test_command` очищается до `uv run pytest -q`.
2. Конституция (`spec/maestro-constitution.md`) переписывается: п. 2–4 сейчас
   инструктируют агента звать `tdd_gate.py red` и описывают наши remedy. В
   штатном режиме red авторствует отдельный пас, а от агента требуется маркер
   `TDD_SELECTOR: <selector>`.
3. `harness_files` пересобирается: пути нашего гейта уходят, появляется вопрос,
   что вообще осталось защищать (§4.5 — существенно меньше).
4. **Экспортёр evidence** — новый маленький артефакт вместо 1997 строк:
   выгрузка `red_checkpoints`/`tdd_claims`/`tdd_remedies`/`tdd_phases` в
   трекаемые JSON-файлы репо. Читать можно из двух мест: живой БД в worktree
   (до уборки) или post-mortem архива (после) — второе устойчивее, потому что
   архив гарантирован инвариантом #164, а момент уборки — нет. Без экспортёра
   §5.1 остаётся в силе; с ним свойство «evidence мержится вместе с работой»
   сохраняется при кратно меньшем коде.
5. Прогон-доказательство: минимум одна leaf-задача в штатном режиме с полной
   цепочкой, прежде чем удалять наш гейт.

**Что удаляется по итогам:** `scripts/tdd_gate.py` (1997), `tests/harness/`
(2725, 130 тестов), `spec/plugins/tdd-gate/`. Порядок обратный интуиции:
сначала прогон-доказательство, потом удаление.

## 7. Открытые вопросы

- **Кто пишет экспорт и откуда читает** — hook spec-runner на завершении
  задачи (живая БД) или отдельный шаг по post-mortem архиву. Это развилка §5.1
  и главный неотвеченный вопрос оценки. Чтение из архива не требует правок у
  соседей, чтение из живой БД — вероятно, требует.
- **Историческая evidence** (100/102/6 файлов) — конвертировать, оставить как
  архив прошлого формата или заморозить с пометкой. Склоняюсь ко второму:
  переписывать историю сертификации нельзя.
- **Независимость судьи** (§5.3) — принять как приемлемую или сохранить
  минимальный внешний replay-верификатор поверх штатных чекпоинтов.
- **Экспериментальный статус** (§5.5) — нужен ли пин версии spec-runner в
  дев-контуре disputatio, раз мы зависим от нестабильных таблиц.

## 8. Вывод

Штатный контракт покрывает **все** механизмы нашего гейта и по четырём
позициям строго сильнее: точка отказа до реализации (закрывает наш же
blocking finding D4), учёт денег, пиновка политики, иммунитет харнеса к
агенту. Разработка альтернативы своими силами больше не оправдана.

Единственная содержательная потеря — не функция и не живучесть (архив
#164 гарантирован и невыключаем), а **класс артефакта**: evidence перестаёт
быть трекаемым содержимым репо и становится машинно-локальным архивом с
ротацией `keep_per_workstream: 5`. Она не мержится, не видна в ревью и не
переживает снос воркспейса. Для сертификационной ступени это дороже, чем
любой отдельный выигрыш из §4, и именно поэтому миграция не сводится к правке
конфига.

**Рекомендация — гибрид, а не «или-или»:** принять `execution_mode: tdd` как
исполняющий гейт и заменить 1997 строк не нулём, а маленьким экспортёром
evidence. Порядок: конфиг → конституция → экспортёр → прогон-доказательство →
удаление гейта. До прогона-доказательства ничего не удалять.

Побочно: `todo://disputatio/tdd-gate-red-supersede` после этого почти наверняка
закрывается штатными `tdd resume`/`repair`/`release` (§4.4) — но подтверждается
это тем же прогоном, а не текстом этой оценки.
