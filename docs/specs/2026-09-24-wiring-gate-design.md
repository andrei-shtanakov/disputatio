# Гейт покрытия «объявлено, но не подключено» (`disp gate wiring`)

Статус: draft v0.1 · Дата: 2026-09-24
Пункт плана: `todo://disputatio/gate-declared-not-wired` (issue #60).
Место в системе: дополнительный doc-гейт сверх baseline, SPEC-002 §6.
Ядро, runner, `DocVerifier` и схема конфига §3.2 не меняются.

---

## 1. Задача и граница

Цикл полировки пары SPEC-002 v0.2 + план (PR #54) прошёл 11 раундов
author↔reviewer и сошёлся, после чего терминальные ревью PR нашли дефекты,
которые оба агента пропустили. Разногласия не было: оба сверяли документ с
документом, а дефект жил в связи документа с кодом, которого никто не менял.
Два таких дефекта машинно проверяемы и служат **обязательными приёмочными
примерами** (§7):

- **второй конструктор.** SPEC-002 P10 объявляет, что политику возврата
  конструирует только composition root. На снимке `23c9297` (база PR #54)
  класс `ArchitecturalDefectPolicy` конструировался в файле
  `src/disputatio/runtime/pipeline_runner.py` дважды: строки 581 и 1071.
  План снимал только первую.
- **неполное перечисление.** Редакция v0.2 добавляла пятую append-only
  коллекцию `doc_sessions`. На том же снимке функция `_guard_history` в
  `src/disputatio/events/pipeline_store.py` (строка 109) проверяла четыре
  коллекции поимённо, и план пятую туда не добавлял.

Гейт делает одно: **перечисляет места в текущем коде, где нарушен
машиночитаемо объявленный инвариант спеки, и проверяет, что каждое такое
место структурно связано с задачей плана.**

Гейт **не доказывает**:

- что действие задачи существует и корректно. Проверяемая связь
  структурная: задача существует, и в её разделе есть ссылка на место (§5);
- что инвариант нельзя нарушить путями, которые анализ не видит (§3.3);
- ничего о произвольных архитектурных утверждениях. Гейт понимает ровно два
  вида правил (§3).

Вне v1: правило «константа без потребителя» (класс `EDGES_BY_KIND`), линт
над `src/` на стадии кода, общий движок для двух режимов, арбитр SPEC-001,
erratum к §10 SPEC-001, правило «внешний прогон до объявления сходимости».

## 2. Подключение и входы

Гейт — подкоманда CLI:

```
disp gate wiring --spec <путь> --plan <путь> [--src <каталог>]
```

Оператор подключает её в конфиге пайплайна вида `pair` как обычный
дополнительный гейт:

```toml
[[pipeline.gates]]
name = "wiring"
cmd = "disp gate wiring --spec docs/specs/x-design.md --plan docs/plans/x-plan.md"
```

Гейт запускается штатным `run_gate` в корне репозитория (`repo_root`), и
результат отображается по его контракту: код `0` → `pass`, иначе `fail`,
хвост вывода идёт в отчёт.

- `--spec` — документ с блоком правил (§3.1).
- `--plan` — документ с блоком покрытия (§5.1).
- `--src` — каталог корня импорта относительно корня репозитория, по
  умолчанию `src`. Модульное имя файла выводится относительно него:
  `src/disputatio/events/pipeline_store.py` → `disputatio.events.pipeline_store`,
  `__init__.py` даёт имя пакета.

Пути `--spec` и `--plan` задаются относительно корня репозитория. Файл не
существует, не читается или не декодируется как UTF-8 — код `2`.

Анализируется только `--src`. Файлы вне него, включая `tests/`, в
перечисление нарушений не входят: конструирование в тесте не считается
производственным подключением.

Вид `document` гейт не обслуживает: у вида нет плана, покрывать нечем.

### 2.1 Запуск бинаря и `skip`

`run_gate` разбирает `cmd` через `shlex.split` и запускает без shell
(`Popen(shell=False)`), бинарь ищется по `PATH` процесса оркестратора.
Если `disp` там нет, запуск не состоялся: `run_gate` отдаёт `skip`, а не
`fail`. Этот `skip` **не блокирует сходимость**: `skip` дополнительного
гейта при зелёном baseline даёт общий `pass` (SPEC-002 §6). Менять эту
семантику гейт не вправе, это ядро.

Отсюда два обязательства оператора, записанные в документации (§9):

- `cmd` обязан находить ту же установку `disp`, что ведёт пайплайн. Запуск
  пайплайна через `uv run disp …` кладёт `.venv/bin` в `PATH`, и голое имя
  `disp` находится. При запуске родителя абсолютным путём `cmd` пишется с
  тем же абсолютным путём;
- подключение проверяется по первому раунду: в `verification.json` гейт
  `wiring` обязан иметь статус `pass` или `fail`. `skip` значит, что гейт не
  запускался, и такой раунд о покрытии не говорит ничего.

## 3. Правила

### 3.1 Блок правил в спеке

Спека несёт **ровно один** fenced-блок с info-строкой `disputatio-wiring`,
содержимое — TOML. Нет блока, их два и больше, TOML не разбирается —
код `2` (§6).

Пример (в самой этой спеке блок помечен `toml`, чтобы гейт его не читал):

```toml
[[rule]]
id = "p10-policy"
kind = "construct-only-in"
class = "disputatio.runtime.pipeline_runner:ArchitecturalDefectPolicy"
allowed = ["src/disputatio/runtime/composition.py"]

[[rule]]
id = "append-only-guard"
kind = "enumerates-all"
module = "src/disputatio/events/pipeline_store.py"
function = "_guard_history"
checkers = ["_guard_sessions", "_guard_immutable"]
members = ["spec_sessions", "pair_sessions", "doc_sessions",
           "transitions", "operator_decisions"]
```

Схема закрыта. Массив `rule` обязателен и непуст: блок без правил
(`rule = []` или без ключа `rule`) давал бы зелёный результат без единой
проверки, и обязательность блока ничего бы не значила. Пустой или
отсутствующий `rule`, неизвестный ключ, неизвестный `kind`, отсутствующее
обязательное поле, пустой `allowed`/`checkers`/`members`, повтор `id`,
повтор элемента внутри `allowed`, `checkers` или `members` — код `2`.
Повтор элемента запрещён, потому что делает счёт нарушений и покрытия
неоднозначным: один член, названный дважды, дал бы два нарушения с одним
ключом. `id` — `[a-z0-9][a-z0-9._-]{0,63}`.

### 3.2 `construct-only-in`

Поля: `class` — полное имя `модуль:qualname`, `allowed` — список файлов
относительно корня репозитория.

**Нарушение** — строка файла под `--src`, не входящего в `allowed`, на
которой есть хотя бы один узел `ast.Call`, чья вызываемая часть
разрешается (§3.4) в объявленный класс. Несколько таких вызовов на одной
строке — **одно** нарушение с числом вызовов `count`: координата
нарушения — `путь:строка`, и различать вызовы внутри строки ею нельзя.
Строка вызова — `lineno` узла `Call`.

Предусловия, нарушение которых даёт код `2`:

- модуль класса есть в снимке;
- в нём есть класс верхнего уровня с этим именем. qualname с точкой
  (вложенный класс) в v1 не поддерживается;
- каждый путь из `allowed` есть в снимке.

### 3.3 Граница гарантии `construct-only-in`

Перечисляются только **прямые синтаксические вызовы**, разрешённые по
§3.4. Не видны и потому не дают нарушения:

- присваивание класса или модуля другому имени и вызов через него
  (`P = C; P()`, `m = mod; m.C()`);
- `getattr`, `type(x)()`, `functools.partial`, фабрики, `eval`,
  `importlib.import_module`;
- альтернативные конструкторы (`C.from_x()`);
- конструирование подкласса;
- реэкспорт класса снимка внешним модулем (внешние модули не
  исследуются).

Это объявленная граница, а не дефект. Гейт утверждает: «прямых вызовов
конструктора вне `allowed` нет, кроме покрытых планом», — а не «объект
нигде больше не создаётся».

Ложные срабатывания возможны по двум причинам, обе следуют из
консервативного объединения привязок (§3.4): локальное переопределение
имени внутри функции (параметр или присваивание) не отслеживается, а
одноимённые импорты из разных областей видимости модуля объединяются.
Такие срабатывания громкие, а не тихие, поэтому допустимы.

### 3.4 Разрешение имён

Разрешение статично и идёт по снимку (§4). Объекты разрешения:
**класс** `модуль:имя`, **модуль** `имя.модуля` и **внешний** (всё, чего
нет в снимке). Результат разрешения — **множество** объектов.

**Модули снимка** — каждый `.py`-файл под `--src` и каждый пакет. Пакет —
каталог с `__init__.py` либо **namespace-пакет**: каталог под `--src` без
`__init__.py`, в котором на любой глубине есть `.py`-файл. Namespace-пакет
— модуль без собственных привязок: `import pkg.impl; pkg.impl.C()` при
`src/pkg/impl.py` без `pkg/__init__.py` разрешает `pkg` в модуль снимка, а
не во внешний, и вызов засчитывается. Сам корень `--src` модулем не
является.

**Привязки модуля `M`** — отображение имени в список источников. Собираются
со всего дерева модуля, включая тела функций и классов:

| Оператор | Имя | Источник |
|---|---|---|
| `class N` на верхнем уровне | `N` | класс `M:N` |
| `from X import N as A` | `A` (без `as` — `N`) | член `(X, N)` |
| `import X.Y as A` | `A` | модуль `X.Y` |
| `import X.Y` | `X` | модуль `X` |

Относительный `from`-импорт разрешается от пакета `M` (для `__init__.py`
— от самого пакета). Выход за корень `--src` — код `2`.

**`from X import *`**, где `X` — модуль снимка, — код `2`: его привязки
статически не перечислимы без правил `__all__`, а молча пропустить их
нельзя. Звёздочный импорт внешнего модуля игнорируется: внешние модули не
исследуются, и всё, что приходит из них, считается
внешним, даже если внешний пакет реэкспортирует класс снимка. Это граница
анализа (§3.3). На снимке `23c9297` звёздочных импортов нет.

**`resolve(M, n)`** — объединение по всем источникам имени `n` в `M`:

- класс → он сам;
- модуль → он сам, если он есть в снимке, иначе внешний;
- член `(X, N)` → `member(X, N)`.

**`member(X, N)`** — что значит `X.N`:

1. `X` нет в снимке → внешний;
2. иначе объединение `resolve(X, N)` и модуля `X.N`, если такой модуль
   есть в снимке. Пусто → внешний.

**Атрибут** `a.b.C` разрешается по звеньям: `S₀ = resolve(M, a)`, затем
для каждого звена `k` множество `Sᵢ₊₁` — объединение `member(X, k)` по
всем модулям `X ∈ Sᵢ`. Классы и внешние объекты в `Sᵢ` атрибуты не
разрешают и дают внешний. Этим покрыт и модульный алиас в пакете:
`pkg/__init__.py` с `import impl as alias` и вызов `pkg.alias.C()` дают
`resolve(pkg, alias) = {модуль impl}`, затем `member(impl, C)`.

**Циклы.** Ключ обхода — тройка `(операция, модуль, имя)`, где операция —
`resolve` или `member`. Отсекается только повторный вход в ключ, который
лежит **в активном стеке рекурсии**: такой вход даёт пустое множество, а
ключ снимается со стека при возврате. Переход `member(X, N)` →
`resolve(X, N)` поэтому циклом не считается: у них разные ключи. Каждый
самостоятельный запрос (разрешение одного `func` одного вызова) начинает
обход с пустым стеком; накопленного между запросами множества нет.
Циклический реэкспорт класс не определяет, поэтому пустота на настоящем
цикле честна, а класс, достижимый по другой ветви того же цикла, этой
ветвью находится.

**Вызов** засчитывается, когда множество разрешения его `func` (`Name`
через `resolve`, `Attribute`-цепочка с корнем `Name` через звенья)
**содержит** объявленный класс. Прочие формы `func` (вызов результата
вызова, подписка) не разрешаются. Внутренний `Call` цепочки
`C().method()` при этом разрешается сам по себе.

**Совпадение короткого имени не даёт нарушения.** Класс с тем же `N` в
другом модуле разрешается в другое полное имя, внешний `N` — во внешний.

### 3.5 `enumerates-all`

Поля: `module` — файл относительно корня репозитория; `function` —
qualname функции в нём (`f` или `Class.method`); `checkers` — имена
проверяющих вызываемых, как они записаны в теле; `members` — объявленный
состав.

Правило проверяет **фактический перебор**, а не присутствие имён.
Поддерживается ровно одна форма тела:

1. необязательный докстринг первым оператором;
2. затем только операторы-выражения `ast.Expr(ast.Call)`, где `func` —
   `ast.Name` с `id` из `checkers`, — **проверяющие вызовы**.

Член проверяющего вызова — `attr` его позиционных и именованных аргументов
вида `ast.Attribute(value=ast.Name(id=p), attr=m)`, где `p` — параметр
функции. У вызова должен быть хотя бы один такой аргумент, и все такие
аргументы обязаны нести один и тот же `attr`. Прочие аргументы (строковые
литералы, константы) игнорируются.

Не засчитываются по построению: строки докстринга и диагностики, имена во
вложенных функциях, лямбдах, comprehension'ах и под условием.

**Неподдерживаемая форма молча успехом не считается.** Если тело содержит
любой другой оператор (цикл, `if`, присваивание, `return`, вызов не из
`checkers`, вложенный `def`), либо проверяющий вызов не имеет члена или
несёт два разных, место получает находку `unverifiable` (§6). Её нельзя
покрыть планом: это отказ гейта судить, а не нарушение. Лечится правкой
правила.

**Нарушение** — каждый член `members`, которого нет среди членов
проверяющих вызовов. Координата — `путь:строка` оператора `def`
(`lineno` узла функции) плюс `member`.

Члены, проверяемые сверх `members`, не нарушение. Функции нет в модуле,
или модуля нет в снимке, — код `2`. Искомое имя (функция, а для
`Class.method` — и класс в модуле, и метод в теле класса) обязано быть
привязано в своей области видимости **ровно одним безусловным
определением** — `def`/`async def` (для класса — `class`) прямо в теле
модуля или класса. Иначе — тоже код `2`: несколько определений; условное
определение, даже единственное (под `if`/`elif`/`else`,
`try`/`except`/`else`/`finally`, `try*`, `with`, `for`/`while` с их
`else`, `case` оператора `match` на любой глубине); перепривязка имени в
той же области (присваивание, в том числе аннотированное, составное и
`:=`, импорт, `del`, цель `for`/`with`/`except … as`/`case`, одноимённый
`class`). Python связывает то, что выполнилось последним, а условное
определение статически не разрешается: молчаливый выбор одного узла читал
бы не ту функцию. Тела вложенных `def`/`class`/`lambda` и переменные
comprehension'ов — другая область видимости и не учитываются.

## 4. Снимок кода

Строки координат имеют смысл только на конкретном коде, поэтому проверка
привязана к снимку:

- **отпечаток** — `git rev-parse HEAD:<src>`, sha дерева каталога `--src` в
  `HEAD`. Коммиты, меняющие только документы, его не меняют: раунды
  полировки пары не инвалидируют покрытие;
- **чистота** — `git status --porcelain --untracked-files=all -- <src>`
  обязан быть пуст. Это учитывает staged, unstaged и untracked файлы.
  Игнорируемые файлы в анализ не попадают вовсе (см. ниже);
- **источник анализа** — объекты git этого дерева (`git ls-tree -r`,
  `git cat-file`), а не файловая система. Анализируется ровно то, что
  зафиксировано отпечатком;
- **read-only** — гейт не пишет ни в рабочее дерево, ни в индекс, ни в
  `.git`. Все вызовы git идут с `GIT_OPTIONAL_LOCKS=0`: без него `git
  status` вправе обновить индекс, освежив в нём stat-данные.

Отпечаток плана не совпал с `HEAD:<src>` → находка `stale-snapshot`. `src`
грязный → находка `dirty-src`. Любая из них — код `1`, и покрытие тогда не
вычисляется: координаты неизвестного кода ничего не значат.

Код `2` дают и условия окружения, при которых снимок нельзя собрать
честно:

- не git-репозиторий, нет `HEAD`, нет каталога `<src>` в `HEAD`;
- `--root` — не корень рабочего дерева (`git rev-parse --show-prefix`
  непуст): `git ls-tree` ограничил бы выдачу подкаталогом, а `HEAD:<src>`
  разрешается от корня, и снимок вышел бы пустым;
- бинарь `git` не найден или не запускается, либо вызов git завершился
  ошибкой;
- в дереве `<src>` есть подмодуль (gitlink): его содержимое в объектах
  этого дерева отсутствует, и молча пропустить его значило бы не
  анализировать часть `src`;
- в дереве `<src>` есть `.py`-запись-symlink: её блоб — текст пути
  назначения, а не исходник, и прочитать его как код или пропустить нельзя.
  Symlink без суффикса `.py` игнорируется, как любой не-`.py`-файл;
- путь в дереве не декодируется строгим UTF-8: при замене символов разные
  байтовые имена совпали бы, и один файл пропал бы из снимка.

**Разбор исходников.** Анализируются все `.py`-файлы дерева `<src>`, без
исключений и лениво не пропуская ни один: пропущенный файл мог бы скрыть
конструктор. Байты блоба отдаются `ast.parse` напрямую, поэтому кодировка
определяется по PEP 263 (BOM, `coding`-cookie, иначе UTF-8). Синтаксис —
грамматика интерпретатора, в котором работает `disp` (проект требует
Python ≥ 3.12). Любой файл, который не декодируется или не разбирается, —
код `2` с именем файла. Остальные файлы дерева игнорируются.

**Коллизия модульных имён** — два файла снимка с одним модульным именем
(`src/pkg.py` и `src/pkg/__init__.py`; `src/x.y.py` и `src/x/y.py`) — код
`2` с именами обоих файлов. Индекс по имени модуля хранит один файл, и
второй выпал бы из анализа молча; какой из них «настоящий», статически
решать гейт не берётся. Обычный модуль рядом с одноимённым namespace-
каталогом (`src/pkg.py` и `src/pkg/impl.py` без `__init__.py`) коллизией
не считается: у файлов разные модульные имена, и анализируются оба.

## 5. Покрытие

### 5.1 Блок покрытия в плане

План несёт **ровно один** fenced-блок с info-строкой
`disputatio-wiring-cover`, содержимое — TOML:

```toml
src_tree = "70637371794b53ddc85dffb10624838e53ffb07c"

[[cover]]
rule = "p10-policy"
site = "src/disputatio/runtime/pipeline_runner.py:581"
task = 5

[[cover]]
rule = "append-only-guard"
site = "src/disputatio/events/pipeline_store.py:109"
member = "doc_sessions"
task = 1
```

`src_tree` обязателен. `member` обязателен для `enumerates-all` и запрещён
для `construct-only-in`. `task` — номер задачи, целое ≥ 1. Схема закрыта;
нарушение формы — код `2`.

### 5.2 Ключ нарушения

Нарушение и запись покрытия сопоставляются по ключу
`(rule, site)` для `construct-only-in` и `(rule, site, member)` для
`enumerates-all`. `site` — `путь:строка`, путь относительно корня
репозитория. По §3.2 ключ `construct-only-in` однозначен: несколько вызовов
на строке — одно нарушение.

### 5.3 Что проверяется

1. **Непокрытое** (`uncovered`): у нарушения нет записи.
2. **Дубль** (`duplicate-cover`): у ключа больше одной записи.
3. **Висячая запись** (`dangling-cover`): ключу записи не соответствует
   нарушение (места нет, правило не нарушено там, `rule` не объявлен).
4. **Нет задачи** (`missing-task`): в плане нет заголовка задачи с этим
   номером.
5. **Нет ссылки в задаче** (`site-not-in-task`): в разделе задачи не
   встречается строка `site` (для `enumerates-all` ещё и имя `member`).
   `site` засчитывается только целым токеном — перед ним не `[\w./-]`,
   после него не цифра; `member` — только целым словом (соседние символы
   не `\w`).

**Заголовок задачи** — строка `### Задача N:` или `### Task N:`, где `N` —
номер. **Раздел задачи** — текст от её заголовка до следующего заголовка
уровня 1–3. Заголовки распознаются по CommonMark: ATX с отступом ≤ 3
и любым пробельным символом после `#`, setext уровней 1–2. Несколько
заголовков с одним номером — код `2`. Текст раздела,
по которому проверяется ссылка, не включает содержимое fenced-блоков, в том
числе самого блока `disputatio-wiring-cover`. Строка фенса (открывающая и
закрывающая) распознаётся по CommonMark — отступ 0–3 пробела; отступ 4+ или
табуляция фенс не открывает и не закрывает, а остаётся текстом раздела.

Проверки 4–5 устанавливают **структурную связь**: задача существует, и её
раздел ссылается на место. Что действие в разделе есть и исправляет
нарушение, гейт не доказывает — это остаётся предметом ревью.

## 6. Вывод и коды выхода

| Код | Когда |
|---|---|
| `0` | снимок свежий и чистый, у каждого нарушения ровно одна запись, висячих нет, все задачи и ссылки на месте, `unverifiable` нет |
| `1` | есть хотя бы одна находка: `uncovered`, `duplicate-cover`, `dangling-cover`, `missing-task`, `site-not-in-task`, `unverifiable`, `stale-snapshot`, `dirty-src` |
| `2` | декларации, входы или окружение непригодны: `--spec`/`--plan` не читаются, нет или несколько блоков, битый TOML, нарушение схемы, класс/модуль/функция/путь `allowed` не найдены в снимке, неоднозначный qualname, повтор элемента в `allowed`/`checkers`/`members`, повтор номера задачи, исходник или путь снимка не декодируется (путь — строгий UTF-8) или исходник не разбирается, коллизия модульных имён, `.py`-symlink или подмодуль в `<src>`, звёздочный импорт модуля снимка, относительный импорт за корень, `--root` не корень рабочего дерева, `git` не найден или вызов git завершился ошибкой (§4) |

Код `2` старше кода `1`: при непригодных декларациях находки не
вычисляются. Необработанное исключение — дефект гейта, а не отказ во
вводе: оно не глушится (как у прочих подкоманд `disp`) и даёт ненулевой
код, то есть `fail`, а не `pass`.

Вывод — stdout, по строке на находку, отсортированно по
`(код находки, rule, site, member)`:

```
uncovered construct-only-in p10-policy src/disputatio/runtime/pipeline_runner.py:1071 count=1
```

Последняя строка — сводка: `wiring: N нарушений, M покрыто, K находок`
(или причина кода `2`). Сводка идёт последней, потому что в отчёт попадает
хвост вывода (`DEFAULT_TAIL_LINES = 200`).

## 7. Приёмка

Приёмочные примеры строятся из **полного** дерева `src` снимка `23c9297`:
оно вендорится в тесты архивом, тест разворачивает его во временный
git-репозиторий и **сверяет отпечаток** с
`70637371794b53ddc85dffb10624838e53ffb07c`. Совпадение доказывает, что
фикстура дословна, а номера строк исторические. Правила — из примера §3.1.
На полном дереве снимка правила дают ровно три нарушения: две строки
конструктора (581, 1071) и `doc_sessions` на строке 109; лишних нет
(сверено по всем 81 модулю снимка).

| Пример | План покрывает | Ожидание |
|---|---|---|
| второй конструктор | только строку 581 | код `1`, `uncovered` на строке 1071 |
| второй конструктор | строки 581 и 1071 | нарушений этого правила без записи нет |
| неполное перечисление | ничего для `_guard_history` | код `1`, `uncovered` на строке 109, `member = doc_sessions` |
| неполное перечисление | строку 109 с `doc_sessions` | нарушений этого правила без записи нет |
| оба правила | все три нарушения, задачи со ссылками | код `0` |

Сопутствующие обязательные случаи (на малых синтетических деревьях):

- конструирование класса в `tests/` не даёт нарушения;
- класс с тем же коротким именем в другом модуле не даёт нарушения;
- реэкспорт через `__init__.py`, `import pkg.mod as m; m.C()` и модульный
  алиас в пакете (`pkg.alias.C()`) дают нарушение;
- цикл реэкспорта, из которого класс достижим по другой ветви, даёт
  нарушение; чистый цикл — не даёт и не зацикливает гейт;
- повторные вызовы через одну и ту же привязку в разных функциях дают
  нарушение каждый (состояние обхода между запросами не копится);
- два конструктора на одной строке — одно нарушение с `count=2`, одна
  запись его покрывает;
- `from <модуль снимка> import *` — код `2`;
- неразбираемый `.py` в `src` — код `2`, а не пропуск файла;
- тело `_guard_history` в форме после фикса (цикл по источнику состава)
  даёт `unverifiable`, а не `0`;
- строка с именем члена в докстринге и во вложенной функции не
  засчитывается;
- правка документа после фиксации отпечатка не меняет результат; правка,
  staged-правка и untracked-файл в `src/` дают `dirty-src`; иной отпечаток
  даёт `stale-snapshot`;
- отсутствие блока правил — код `2`, а не `0`;
- подключение через `[[pipeline.gates]]` и `run_gate` в корне репозитория
  даёт `pass`/`fail`, а не `skip`, то есть команда действительно
  запускается.

## 8. Раскладка

- `src/disputatio/verifier/wiring.py` — разбор блоков, правила, покрытие,
  находки. Чистые функции над содержимым файлов снимка.
- `src/disputatio/verifier/wiring_snapshot.py` — отпечаток, чистота и
  чтение дерева через git.
- `src/disputatio/cli.py` — подкоманда `gate wiring`: аргументы, вызов,
  печать, код выхода.
