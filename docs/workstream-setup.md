# Настройка workstream'а: что обязано быть в гейте до первого агента

Собрано по итогам пилотной волны (семь workstream'ов, 100 задач). Каждый пункт
здесь — не предпочтение, а оплаченный урок: без него волна теряла время или
получала зелёный гейт на негодном состоянии.

`spec-runner.config.yaml` в этом репозитории **gitignored** (он операторский, с
локальными путями), поэтому требования к нему живут здесь, а не в самом файле.
Эталон — `spec-runner.config.example.yaml`.

## 1. Пер-тасковый гейт: pyrefly обязателен

```yaml
executor:
  commands:
    test: uv run python scripts/tdd_gate.py verify && uv run pyrefly check && uv run pytest -q
    lint: uv run ruff check .
```

**Почему не только на приёмке.** В пилоте пер-тасковый гейт был
`tdd_gate verify && pytest`, а typecheck стоял лишь в чек-листе приёмочной
задачи. Типовой долг копился 22 задачи и вскрылся в конце — четырьмя ошибками
в тестах, которые к тому моменту уже были byte-locked, то есть неисправимы без
операторской санкции (см. `abandon`/`repair` в конституции). Цена pyrefly в
цепочке — около 18 секунд на задачу.

**Порядок команд значим.** `pytest` идёт последним: spec-runner умеет
переписывать `test_command`, дописывая пути тест-файлов в конец строки
(scoped-режим), и при другом порядке они уехали бы в аргументы `pyrefly`
(spec-runner#139).

## 2. Control-plane в harness_files

```yaml
  harness_guard: strict
  harness_files:
  - spec-runner.config.yaml      # ← сама политика
  - pyrefly.toml                 # ← послабления typecheck
  - scripts/tdd_gate.py
  - spec/plugins/tdd-gate
  - spec/.tdd-evidence/verdicts
  - spec/.tdd-evidence/waivers
  - spec/.tdd-evidence/abandoned
  - spec/.tdd-evidence/repairs
  - spec/maestro-constitution.md
```

Дефолтный список `HARNESS_CANDIDATES` в spec-runner не включает ни собственный
конфиг, ни `pyrefly.toml`. Агент работает в worktree и технически может
изменить и то, и другое — а сообщение strict-гейта при отказе прямо предлагает
«exempt it via harness_allow» (spec-runner#137).

## 3. Строгий guard не заменяет внешнюю проверку

`harness_guard: strict` снимает snapshot **внутри каждой попытки**, поэтому
запрещённая правка, пережившая упавшую попытку, попадает в baseline следующей и
легализуется (spec-runner#137, наблюдено на регистрации entrypoint в
`pyproject.toml`). До исправления в spec-runner:

- либо `max_retries: 1` на задачах, чей scope пересекается с
  `HARNESS_CANDIDATES`;
- либо внешний immutable pin — хэши оракульных файлов, прибитые оператором один
  раз и лежащие **вне** рабочего дерева, первым звеном `test_command`.

Оговорка: pin — аварийная компенсация, а не граница доверия. Процессы того же
пользователя могут изменить и сам верификатор. Настоящее решение —
инструментальное, вне author-controlled окружения.

## 4. Preflight, которого нет: scope × HARNESS_CANDIDATES

Перед запуском волны сверить declared scope каждой задачи с оракульной
поверхностью. Задача, обязанная править файл из `HARNESS_CANDIDATES` (типичный
случай — регистрация entrypoint в `pyproject.toml`), при `strict` невыполнима
по построению. Это видно статически, за секунды; в пилоте выяснилось тремя
провалившимися попытками.

## 5. Инвариант владения тест-файлами

> Каждый тест-файл имеет **единственного task-owner** и объявлен в scope.

Формулировка «одна задача — один файл» неверна и запрещает безобидное: владеть
несколькими файлами одной задачей безопасно. Опасны две другие вещи:

- **совместное владение** — две задачи пишут в один файл, и поздняя запирает
  раннюю через byte-lock (в волне 1 сработало трижды на одном I001);
- **неучтённый файл** — не попал ни в матрицу трассируемости, ни в scope, и
  приёмка его не видит.

Приёмочная задача обязана проверять обе половины: orphan-детектор (каждый
модуль присутствует в матрице REQ → модуль) и границы scope.

## 6. Приёмка не должна переживать свой workstream

Проверки границ scope сравниваются с базой (`pilot/wave-1`), а после интеграции
эта ветка удаляется по правилу полирепо. Тест, требующий ссылку жёстко, станет
вечно красным на `master`. Правильно — скипать с явной причиной: границы не
нарушены, сравнивать не с чем.

## 7. Наблюдение и барьер

- **Один владелец наблюдения**: один процесс раннера, один лог, один Monitor.
  В пилоте накапливалось до трёх мониторов на один лог — дубли событий и риск
  конфликтующих реакций.
- **Внешний watchdog с критерием `completed < planned`**, отвязанный от
  харнесса. `on_task_failure: stop` фактическую остановку не гарантирует
  (spec-runner#136), а ревью не блокирует задачу ни при каком исходе
  (spec-runner#138) — то есть встроенных барьеров, по сути, нет.
- Считать закрытые задачи **только по meta-строкам задач**
  (`^- .*\| ✅ DONE`), а не по всему файлу: строка легенды в шаблоне тоже
  содержит `✅ DONE`, и наивный счёт даёт +1 — барьер промолчал бы ровно на
  последней незакрытой задаче.
